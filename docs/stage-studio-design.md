# Stage Studio 設計書

更新日: 2026-08-06
対象: Stage Studio MVP と対象ゲームのカスタムバトル連携

## 1. 目的と設計原則

Stage Studioは、iPhone・Androidスマートフォンだけでステージを作成し、JSONまたはZIPで共有し、対象ゲームのカスタムバトルへ読み込む静的Webアプリである。通常利用にアカウント、開発環境、外部サーバー、AI APIは必要ない。

MVPでは、最初に「生成または手描き → 出撃地点 → 風 → テスト砲撃 → 検証 → 出力 → ゲームへインポート → 1試合開始」の縦の流れを完成させる。公式ステージ、通常対戦、ランク相当の導線にはカスタムステージを混入させない。

## 2. リポジトリ調査結果

### 2.1 ビルド・公開・テスト

- ゲーム本体の入口はルートの `index.html`。HTML、CSS、JavaScriptを1ファイルに収めた静的ブラウザゲームである。
- 調査開始時点では`package.json`とlockファイルはなく、ゲーム本体にビルド工程はなかった。
- ルートに`manifest.webmanifest`と`sw.js`があり、ゲーム本体はPWA用のマニフェストとService Workerを既に持つ。
- 公開時のキャッシュ更新は、`index.html`の`BUILD_ID`とルート`sw.js`のキャッシュ名を同じ版へ進める運用である。Stage Studioは子スコープの独立したキャッシュ名を持ち、ゲーム側Service Workerのナビゲーションフォールバック対象から除外する。
- 調査開始時点では`.github/workflows`は存在せず、GitHub Actionsによる公開定義もなかった。MVPでは回帰とモバイルE2E用のCIを追加したが、自動公開処理は追加していない。公開物は引き続き静的ファイルとして配信できる。
- 既存の自動テストは、`tests/seatharness.js`が`index.html`のインラインスクリプトをNode上へ読み込み、DOM、Canvas、Audio等をスタブして実行する。
- 既存の主要検証コマンドは、`seattest.js`のp1/e1、`regressiontest.js`のp1/e1、`resulttest.js`、`loopbacktest.js`、`stage3test.js`。現行の回帰集計には`lobbysimtest.js`も含める。
- 既存Nodeテストは見た目を検査しない。Canvasの表示、safe area、タッチ操作、PWA、共有シートは実ブラウザまたは実機で別途確認する必要がある。
- ゲームのモバイル表示は`index.html`内のCSSとviewport設定で制御される。調査開始時点のゲーム本体には、カスタムステージ用IndexedDB、ファイル入出力、独立したステージ管理画面はなかった。

Stage Studio追加後も、ゲーム本体はビルドなしで開ける。開発用のnpm依存はローカルHTTPサーバーとPlaywrightだけで、配信物の実行依存にはしない。

### 2.2 現在のステージ構造

ゲーム本体の主要定数は次のとおり。

| 項目 | 現在値 |
|---|---:|
| 論理Canvas | 540 × 960 px |
| ワールド幅 | 1440 px |
| 操作パネル開始Y | 660 px |
| 落下死亡線 | 636 px |
| 地形下端 | 636 px |
| 地形列幅 | 3 px |
| 地形行高 | 4 px |
| 地形列数 | 480 |
| ユニット半径 | 16 px |
| 対応人数 | 1対1または2対2、最大4体 |

座標原点は左上、Xは右向き、Yは下向きである。Canvas全体の高さ960pxには下部操作領域が含まれるため、Stage Studioの編集・戦闘領域は高さ660px、地形の物理下端は636pxとして扱う。ゲーム内の`FLOOR_Y=960`は地面がないことを示す番兵値でもあり、カスタム地形の下端には使用しない。

地形の正本は、各列に0個以上の区間を持つ配列である。

```text
segments[columnIndex] = [[topY, bottomY], ...]
```

- 列数は480、1列の幅は3px。
- 1列に複数区間を持てるため、浮島、洞窟、薄い床を表現できる。
- 空配列の列は奈落になる。
- `buildTerrainMask()`が区間列からオフスクリーンCanvasと`Uint8Array`の衝突グリッドを構築する。
- `surfaceY`は各列の最上面キャッシュであり、`groundYAt()`、歩行、スポーンに使われる。
- `isSolidAt()`が砲弾と地形の衝突判定を行う。
- `walkableGroundYAt()`と`groundYBelow()`が多層地形上の移動と落下を扱う。
- `carveCraterInternal()`が円形にCanvasを消去し、同じ範囲の衝突グリッドを空洞化する。
- `currentSegments`は破壊前地形、`craterHistory`は試合中の破壊履歴として分かれている。

したがって、MVPの正規地形表現には既存と互換な`column-segments`を採用する。編集時は軽量なグリッドへ変換し、保存時に区間列へ戻す。

### 2.3 現在のステージ生成と見た目

ゲーム本体の既存パターンは、左高台、右高台、中央山、中央谷、丘陵、大橋、闘技場とランダムである。`baseCurve()`、`midpointDisplacement()`、`generateTerrain()`が基本曲線、揺らぎ、浮島、空洞、薄床、大橋等を生成する。

既存生成器の大部分は`Math.random()`を使うため、seedだけでは再現できない。Stage Studioでは`seed + generatorVersion + preset + generationParameters`を入力にし、32bit FNV-1aで初期状態を作る`mulberry32`の決定的PRNGを使用する。既存の公式生成器は変更せず、Stage Studioで生成した最終区間列をゲームへ渡す。

ゲーム本体の背景テーマはgrass、desert、snow、volcanicである。これらの戦闘背景は`index.html`内の配色とCanvas描画で生成され、テーマ別の背景画像ファイルは置かれていない。`assets/wall.jpg`は既存の壁面演出用画像で、カスタム背景には転用しない。bossArenaは公式の闘技場専用背景として存在するが、MVPのカスタム背景許可リストには含めない。地形テーマは現状、見た目だけを変え、摩擦やダメージ等の素材物理は変えない。

### 2.4 物理処理

既存物理の主要定数は次のとおり。

| 項目 | 現在値 |
|---|---:|
| 固定ステップ | 1/120秒 |
| 重力 | 650 px/s² |
| 最大風加速度 | 260 px/s² |
| ドラッグから初速への倍率 | 7.8 |
| 砲弾半径 | 5 px |
| 通常弾の地形破壊半径 | 44 px |

`computeLaunchVelocity()`、`stepWorldPhysics()`、`drawTrajectoryPreview()`、`explodeAt()`、`isSolidAt()`が、初速、固定刻み更新、弾道表示、爆発、衝突を担当する。砲弾更新は風と重力を速度へ加算してから位置を進める半陰的オイラー法である。

Stage Studioの共通モジュール`shared/stage-core.js`は同じ定数と計算を公開し、Studioのテスト砲撃とゲーム用アダプターが同じ境界を使う。ゲーム本体の特殊技や通信状態を含む巨大な`stepWorldPhysics()`全体は複製しない。MVPのテストプレイは通常弾相当の弾道、地形衝突、円形破壊、落下を対象とし、特殊技の再現は範囲外とする。

### 2.5 出撃地点とギミック

ゲームはp1、e1、p2、e2の最大4体に対応する。専用の`MAX_PLAYERS`定数は元コードになかったため、共通基盤では既存スロット順から上限4を定義する。出撃地点は地形構築後に地面へ吸着させ、画面外、地形内部、重なり、地面なし、崖付近を検査する。

MVPで出力できる素材とギミックは、ゲームで確実に処理できるものだけに限定する。

- 地形素材: 通常の破壊可能地形`destructible`のみ。
- 背景: grass、desert、snow、volcanic。
- ギミック: ステージ全体へ作用する`globalWind`のみ。方向は左`-1`または右`1`、強さは0以上1以下。無風はギミックを省略するか強さ0で表す。

氷、沼、跳ねる床、ダメージ床、ワープ、回復地点、移動床、一方通行、ターン崩壊、局所風、重力変化はゲーム本体に汎用実装がないため、Studioでは将来機能と表示してもMVPデータへは含めない。

### 2.6 現在の読み込み経路

既存ゲームに独立したステージファイルローダーはない。

1. `buildSnapshot()`が地形、クレーター、ユニット、風、カメラ等を試合スナップショットへまとめる。
2. `applySnapshot()`が試合全体を復元する。
3. `loadTerrainFromSave()`が破壊前の区間列を描画・衝突マスクへ変換し、クレーターを再適用する。
4. フリーモード開始時は`resetMatch()`がパターンを選び、`newTerrain()`を呼ぶ。

カスタムステージは任意のスナップショットを直接`applySnapshot()`へ渡さない。専用スキーマで厳格に検証し、`toGameAdapter()`で既存の`segments`、テーマ、スポーン、風へ変換してから、既存の地形構築処理を呼ぶ。

## 3. 採用アーキテクチャ

```text
schemas/stage.schema.json
          │
shared/stage-core.js ── 生成・正規化・検証・ハッシュ・地形/通常弾物理
shared/stage-storage.js ── IndexedDB、移行、下書き/カスタムステージ分離
shared/stage-repository.js ── 保存先provider契約、端末内provider
shared/stage-zip.js ── 制限付きバンドル入出力
          │
          ├── tools/stage-studio/ ── モバイル編集、テスト、保存、共有、PWA
          └── index.html adapter ── インポート、一覧、カスタムバトル読込
```

共通モジュールはブラウザとNodeテストの両方から利用でき、実行時に外部パッケージやAI APIを要求しない。UI、データ、永続化、バンドル、ゲーム変換を分離し、公式ステージの既存生成経路は維持する。

ゲーム管理UIは`StageRepositoryProvider`のCRUD契約だけを参照する。MVPの`LocalStageRepositoryProvider`は`StageStorage`のカスタムステージ領域だけを包み、`network=false`で外部通信を行わない。将来の投稿機能は別providerとして追加できるが、端末保存や公式ステージ領域とは分離する。対戦前照合用には`createStageIdentity()`で`stageId`、`schemaVersion`、`contentHash`、`gameCompatibility`だけを取り出し、`compareStageIdentity()`で4項目すべての一致を確認する。MVPは照合データ構造のみを提供し、送受信は実装しない。

## 4. エディターデータからゲームデータへの変換

1. 編集中は480×165セルの`Uint8Array`を使う。1セルは3×4px。
2. 描画、削除、図形、塗りつぶし等はグリッドへ適用する。
3. Undo/Redoは操作前後の差分または制限付きスナップショットとして保持する。
4. 保存時に各列の連続セルを`[topY,bottomY]`区間へ圧縮する。
5. 座標と数値を小数3桁へ丸め、列、スポーン、ギミックを決められた順序へ正規化する。
6. `checksums.algorithm`は残し、`checksums.contentHash`だけを空文字にした正規化JSONからSHA-256を計算する。
7. ゲーム側でスキーマとハッシュを再検証する。
8. アダプターが`segments`、`themeKey`、`spawnPoints`、`wind`へ変換する。
9. 既存の地形Canvasと衝突グリッドを同じ区間列から再構築する。

この経路により、表示地形と当たり判定が別データから作られることを防ぐ。

## 5. モバイルUI・保存・PWA

- 縦画面を基準とし、主要操作はsafe areaを避けた下部ナビゲーションへ配置する。
- 編集Canvas内だけ`touch-action`を制御し、ページ全体のスクロールは維持する。
- 一本指は描画・配置、二本指はパン・ズーム。拡大縮小ボタンも用意する。
- タップ領域は48px以上、Undo/Redoは編集画面から常に利用できるようにする。
- ページ非表示、操作完了、画面遷移時に下書きを自動保存する。
- IndexedDBを基本保存先とし、利用できない場合は明示的にファイルバックアップを案内する。
- Service Workerはアプリシェルだけを先にキャッシュする。更新は編集中データを保存してから反映し、旧キャッシュを版単位で整理する。
- Web Worker、OffscreenCanvas、Web Share API、`navigator.canShare`等は機能検出し、非対応時も同期処理、通常Canvas、ファイル保存で継続できるようにする。

## 6. iOS・Android共有方式

共有操作は次の順で機能検出する。

1. `navigator.canShare({files})`と`navigator.share({files})`
2. OS共有シート
3. 標準ファイル保存
4. Blobダウンロード
5. JSONテキストのクリップボードコピー
6. コピーAPIがない場合は選択可能なテキスト欄

JSONとZIPは正式なフォールバックであり、独自拡張子だけに依存しない。iOSのWeb Shareやダウンロード挙動はSafariとホーム画面Webアプリで差があるため、押下前に利用可能な方式だけを表示する。Android Share Targetは将来追加できるが、MVPの必須導線にはしない。

MVPの`共有シートを開く`は、容量を抑えた`.stage.json`をファイルとして渡す。ZIPは`ZIPを書き出す`で端末へ保存し、共有先アプリのファイル添付機能から渡す。どちらもゲームとStage Studioへ再インポートできる正式形式である。

## 7. セキュリティ方針

インポートファイルは信頼しない。

- 宣言型JSONのみを受け入れ、JavaScript、HTML、CSS、関数、外部URLを禁止する。
- `eval`と`Function`を使わない。作者名や説明は`textContent`相当で表示する。
- JSONは2MiB、ZIPは6MiB、解凍後は12MiBを上限とする。
- JSON深度、文字列長、配列数、480列、1列32区間・全4096区間、ギミック16件、スポーン4件を上限とする。
- 数値は有限値、座標範囲内に限定する。
- 許可する素材、背景、ギミックをallowlistで照合する。
- ZIP内は相対の固定ファイル名だけを許可し、`..`、絶対パス、ドライブ文字、バックスラッシュを拒否する。
- ZIPの圧縮後・解凍後サイズと重複エントリーを確認し、失敗時は保存前に中断する。
- SHA-256の`contentHash`をゲーム側でも再計算する。
- 任意のリモート画像URLを読み込まない。MVPは利用者画像の同梱を実装しない。
- Stage Studioには外部スクリプト不要のCSPを設定する。

## 8. ゲーム本体への最小変更方針

- カスタムステージ機能はfeature flag境界を持たせる。
- 公式ステージ一覧とカスタムステージ一覧を別管理する。
- インポート済みデータは既存の中断保存キーや公式データへ書き込まない。
- カスタムステージはカスタムバトル、プライベート対戦、テストプレイだけで選択可能にする。
- 通常のランダム選択、公式対戦へ自動混入させない。
- 削除はカスタム保存領域の対象IDだけに限定する。
- 管理画面の各カードと選択中表示に`stageId`、`schemaVersion`、`contentHash`、`gameCompatibility`をテキスト表示する。長いIDは折り返し、利用者入力をHTMLとして描画しない。
- バトル開始直前には保存領域からステージを再読込し、`startSelectedStage()`から`selectStage()`を再実行する。そこで4項目をゲーム用アダプターと照合し、不一致なら開始前に中断する。

## 9. オンライン対戦

既存ゲームにはスナップショット送受信があるが、カスタムステージ配布用の安全なファイル転送基盤はない。MVPでは新しいサーバーを設置せず、同一端末または事前に同じファイルをインポートした端末での利用に限定する。

実装する境界は、`stageId`、`schemaVersion`、`contentHash`、`gameCompatibility`の比較データと照合関数まで。ホストからのJSON送信、招待リンク、ステージID配信、オンライン投稿は将来機能である。同じハッシュが揃わない場合はオンライン試合を開始させない設計とする。

## 10. MVPと将来拡張の境界

### MVP

- 白紙と決定的プリセット生成
- 指での描画・削除、基本図形、Undo/Redo
- 2人または4人の出撃地点
- 通常破壊可能地形、既存4背景、全体風
- 通常弾相当の共通物理テスト
- 自動検証、公平性警告
- IndexedDB下書き
- JSONと制限付きZIPの出力・入力
- Web Shareまたはファイル保存
- ゲーム側のカスタム一覧、選択、ローカルバトル
- PWAアプリシェルとオフライン下書き編集

### 将来機能

- ゲーム本体に存在しない地形素材とギミック
- 利用者画像、署名、オンライン投稿、検索、評価、通報
- QRコードと短縮共有コード
- カスタムステージの自動ネットワーク配布
- 複数端末での完全同期対戦
- 特殊技を含む完全な試合シミュレーション
- OPFS最適化、Share Target、クラウド同期

## 11. 外部通信・費用・未確認事項

- Stage Studioの生成、編集、検証、保存、テスト、出力は端末内で完結し、AI APIを呼ばない。
- MVPの通常利用で有料サービスは不要。
- 公開された静的ファイルの取得以外にStage Studioが必須とする外部通信はない。
- 対象ゲーム本体が既に行うオンライン対戦、ランキング等の通信は、Stage Studioの通常編集処理とは別である。
- PlaywrightのiPhone相当WebKitとAndroid相当Chromiumはエミュレーションであり、実機確認ではない。
- iOS Safari、iOSホーム画面Webアプリ、Android Chrome、Androidインストール済みPWAでの実機QAは未実施として扱い、結果は`mobile-stage-studio-qa.md`へ追記する。
