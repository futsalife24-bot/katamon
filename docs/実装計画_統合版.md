## 1. 統合結論

先に実行するのは、`CURRENT_WORK_STATE.md`の残タスク1〜7である。原則、新企画はその完了後に着手する。残5・6がユーザー側のGAS/Firebase Console操作待ちだけで止まった場合に限り、通信を増やさないキャリアカードとクラッチ称号を先行できる。残タスク自体を完了扱いにはしない。

新企画の採用方針は次のとおり。

- **採用**: 対戦戦績・因縁記録、図鑑を兼ねたキャリアカード、プリセット型カスタムルール、戦場の傷跡、ボスラッシュ、固定シードチャレンジ、次回の風予報、直前ショットリプレイ、クラッチ称号、見た目カスタム。
- **保留**: 少人数協力レイド、ゲーム内リーグ、宣言ショット。
- **却下**: ランダムイベント、能力・パッシブ・必殺技を差し替えるゲームプレイ用ロードアウト、物理を再計算するフルリプレイ、リプレイの永続保存・共有。

重要な縮小判断は2点ある。

1. 「モンスターカスタム」は**見た目だけ採用**する。能力・パッシブ・必殺技の差し替えは、キャラ固有性、CPU照準、スナップショット復元、保守性をまとめて悪化させるため却下する。
2. 「リプレイ」は**同一セッション内の直前ショットだけ採用**する。物理の再シミュレーションではなく、実戦中に描画した軌跡・爆発・ダメージイベントを記録した「イベントテープ」を再生する。永続保存・共有は行わない。

Fable 5反証レビューの必須条件は次のように反映した。

1. ボスラッシュ初回リリースへ、最低1体の「ルールを1つ破るボス」を含める。
2. クラッチ称号を戦績・キャリアカード直後へ前倒しし、直前ショットリプレイもボスラッシュより先にする。
3. 因縁記録はFirebase匿名UIDを使わない。同UIDは現行コードでメモリ内にしか保持されず、ページ再読込でも変わり得るため、端末保存済み`rankingProfile.deviceId`から用途分離したハッシュIDを作る。

### Fable 5とOpus 5で評価が割れた案の確定理由

#### ロードアウト

Fableは、ゲーム体験を守る観点から「まず見た目、能力は小さな横並び、武器は最大2択」を提案した。一方Opusは、差分の小ささから「必殺技だけ差し替える」案を技術的縮小案とした。

実コードでは、必殺技が`CHARACTERS[*].specialVelocityMul`、`launchShot()`のキャラ別分岐、`cpuAutoTurn()`の`straightAim`・風・重力補正へ分散している。キャラ選択画面の`selectStats`も手書きである。したがって、必殺技差し替えは見た目より安くなく、キャラ固有性も弱める。**Fableのゲームデザイン上の警戒を優先し、見た目のみ採用**する。

#### リプレイ

Fableは`buildSnapshot()`、`applySnapshot()`、観戦者用`latestSnapshot`を流用できるため早期採用を推した。Opusは、現行の弾道が可変`dt`で更新され、地形・風・CPUが`Math.random()`へ依存するため、入力から同じ試合を再現できないと指摘した。

コード確認でもOpusの指摘が正しい。`update(dt)`が弾の位置をフレームごとに積分し、`newTerrain()`、`generateTerrain()`、`rollWind()`、`cpuAutoTurn()`が未シード乱数を使う。そこで、**Fableの「名場面を残す」という目的を採り、Opusの「再計算は危険」という技術判断に従う**。実戦中に採取した描画イベントだけを再生する。

#### ボスラッシュ

両者とも採用だが、評価理由が異なる。現状の`isBossMatch`は、10連勝ごとの`tieredBasin`、専用BGM・背景、BOSS表示が中心で、ボス固有能力は持たない。したがってOpusの言う「入口は安い」は正しいが、Fableのいう「ルールを1つ破るボス」まで進めるにはデータ定義とテストが必要である。**既存演出を入口にしつつ、初回リリースから最低1体はルール破りボスを含める中規模案**として採用する。

## 3. 現行コードとの照合と改修分類

分類の意味は次のとおり。

- **流用可能**: 主要な状態・描画・保存経路が既にあり、画面や集計の追加が中心。
- **部分修正**: 既存の基盤は使えるが、複数の状態経路・検証・初期化を同時に直す必要がある。
- **全面改修**: 人数、権威、データモデル、決定性の前提から変える必要がある。

| 案 | 分類 | 実物確認の根拠 |
|---|---|---|
| 見た目カスタム | 部分修正 | `CHARACTERS`と描画資産は流用可能。ただしオンライン表示には`commitOwnCharacter()`、`maybeRevealCharacter()`、`verifyPeerReveal()`、`serializeUnit()`まで必要 |
| 能力・パッシブ・必殺ロードアウト | 全面改修 | `applyCharacter()`がキャラだけからHP・燃料を決定し、`launchShot()`と`cpuAutoTurn()`が必殺へ密結合。`applySnapshot()`もキャラ適用後に値を上書き |
| ボスラッシュ | 部分修正 | `isBossMatch`、`resetMatch()`、`tieredBasin`、ボス背景・BGM・`drawBossBanner()`・BOSS表示を流用可能。ボス進行と固有定義は新規 |
| 直前ショットのイベントテープ | 部分修正 | `launchShot()`、`fireProjectile()`、`update(dt)`、`explodeAt()`、`spawnExplosion()`へ記録口を追加できる。再計算はしない |
| フルリプレイ・永続保存 | 全面改修 | 可変`dt`、未シード乱数、地形破壊、特殊弾の副作用を決定化し、保存形式・移行も持つ必要がある |
| プリセット型カスタムルール | 部分修正 | `freeModeConfig`、`FREE_TERRAIN_OPTIONS`、`WIND_OPTIONS`、`online.settings`を流用できる。スナップショット・ルール検証まで拡張が必要 |
| 少人数協力レイド | 全面改修 | `units.length === 2`、`turnOrder.length === 2`、`p1/e1`固定、観戦席の書込禁止、勝敗3値、CPU AIを全て再設計する必要がある |
| 固定シードチャレンジ | 部分修正 | 演習・地形選択・スコア・中断保存を流用可能。`Math.random()`を直接使う生成・風・CPU判断へシード乱数を注入する必要がある |
| ゲーム内リーグ | 全面改修 | 日程・参加者・シーズン・不戦処理・改ざん許容範囲の永続モデルが存在しない |
| 端末内戦績・因縁 | 部分修正 | `runStats`、`applyStreakResult()`、`RANKING_KEY`、`online.slots`、`firebaseSeatName()`を流用可能。結果の一度だけ記録する共通口が必要 |
| キャリアカード | 流用可能 | `CHARACTERS`、`CHARACTER_LIST`、`drawWheelSelectCard()`、選択画面の説明・能力値、端末内戦績を流用可能 |
| ランダムイベント | 部分修正 | 技術的にはターン境界へ追加可能だが、砲撃の予測可能性とテンポを損なうため実装しない |
| 戦場の傷跡 | 部分修正 | `currentSegments`、`craterHistory`、`loadTerrainFromSave()`は流用可能。`resetMatch()`と`resetFirebaseRound()`の新規地形生成を条件分岐する必要がある |
| 次回の風予報 | 部分修正 | `rollWind()`と`drawWindMeter()`を流用可能。次の風を先に確定し、オンライン・中断保存へ含める必要がある |
| クラッチ称号 | 流用可能 | `checkMatchEnd()`、`judgeByHp()`、`applyStreakResult()`、`drawResultBanner()`、戦績保存へ載せられる |
| 宣言ショット | 部分修正 | 入力UI、命中条件、結果表示、オンライン通知の追加が必要。現時点では仕様確定に至らない |

### 禁止事項との整合

採用案は、課金、ガチャ、スタミナ、ログインボーナス、放置、Pay to Win、リアルタイム化、レベル制、装備厳選を導入しない。チャレンジの「週替わり」は、取り逃しや報酬差を作る運営イベントではなく、日付から同じシードを生成して友人同士で同条件を遊ぶだけとする。全キャラ・見た目項目・ルールは無条件で使用可能とし、アンロック階層を持たない。

### `IDEAS_必殺技.md`との競合整理

- `boom`は現状、送信側が`netSend({ t: 'boom', unitId })`だけを送り、受信側`case 'boom'`が自端末で飛行中の花火の信管を満了させている。このままでは遅延時間ぶん炸裂位置がずれる。**`x/y`を権威座標として必須化するまで、拡散弾系必殺と直前ショットリプレイへ進まない。**
- 新しい拡散・多段必殺は、`launchShot()`のキャラ別分岐、`specialVelocityMul`、`cpuAutoTurn()`の照準補正を同時に更新する。見た目ロードアウトとは混ぜず、必殺1件につき1Issue・1版を守る。
- 永続するフィールド物体を新必殺へ追加する場合は、本書の採用企画とは別に、オンラインSnapshot、Firebase検証、再戦初期化、中断セーブの4経路を必須対象とする。
- 新キャラ追加は`CHARACTERS`だけでは完了しない。`CHARACTER_LIST`、commit/reveal、`database.rules.json`のcharacter許可リストを更新し、Firebase Consoleへ反映する。
- 本書で能力・必殺ロードアウトを却下したため、既存必殺の追加計画と「必殺を別キャラへ付け替える仕組み」は競合しない。キャラ固有必殺としてのみ拡張する。

## 6. 採用案ごとの実装計画

### 6.1 端末内戦績・因縁記録

**採用範囲**

- 通算勝敗、引き分け、使用キャラ、相手別勝敗、直近対戦。
- 保存先は端末内`localStorage`。表示は`firebaseSeatName()`の名前を使う。
- 相手キーにFirebase匿名UIDは使わない。現行の`firebaseAuth`はメモリ内だけで、ページ再読込後の永続IDにならないためである。
- 既存の`rankingProfile.deviceId`から`SHA-256("katamon-rival-v1:" + deviceId)`で用途分離した`rivalId`を作り、既存`presence/lobbyState`へ追加する。生のランキング端末IDや戦績値は相手へ送らない。
- `rivalId`は同じブラウザプロファイル内ではページ再読込後も維持する。端末変更、再インストール、サイトデータ消去後は新しい相手として記録し、同名だけを根拠に自動統合しない。

**変更対象**

- 既存: `loadRankingProfile()`、`sha256Hex()`、`rememberFirebaseName()`、`firebaseSeatName()`、`validateFirebaseMessageDetail()`、`checkMatchEnd()`、`judgeByHp()`、`applyStreakResult()`、`netSyncResult()`、`case 'result'`、`drawResultBanner()`、`renderFirebaseLobby()`、`resetLocalFirebaseRoundState()`。
- ルール: `database.rules.json`の`presence/lobbyState`へ、固定長hexの`rivalId`検証を追加する。Firebase Console反映を完了条件とする。
- 追加予定: `BATTLE_RECORD_KEY`、`localRivalId()`、`rememberFirebaseIdentity()`、`loadBattleRecord()`、`saveBattleRecord()`、`recordMatchResultOnce()`、`opponentRecordKey()`。
- 決着通知の再送や重複受信で二重加算しないよう、`roundId`またはローカル試合IDで一度だけ記録する。

**テスト**

- `tests/resulttest.js`: 勝ち・負け・引き分け・時間切れ・再戦で1回だけ加算。
- `tests/loopbacktest.js`: host/guestの双方が自分視点の勝敗を1回だけ保存。

- `tests/regressiontest.js`: localStorageの破損・旧形式から安全に初期化。

**規模**: 中（2版）。残タスク4として新企画より先に実施。

### 6.6 固定シードチャレンジ

### 6.8 直前ショットリプレイ

**採用範囲**

**テスト**
