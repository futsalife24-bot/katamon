## 現在できること

### ① ゲームシステム

#### 基本ルール

| 項目 | 現在の仕様 |
|---|---|
| 形式 | ターン制の砲撃戦。1対1 |
| 画面 | 縦持ち固定(仮想解像度 540×960)。ステージ幅 1440px をカメラが横スクロール |
| 手番数 | 1体あたり15手番(合計30ターン)。オンラインは10/15/20から選択可 |
| 操作 | 画面下の発射ボタンから指で引っ張って離すスリング式。引っ張り最大130px |
| 移動 | 手番ごとに燃料102px。歩ける傾斜は58度まで。22px以上の段差は落下扱い |

#### 勝敗条件(4通り)

1. 相手のHPが0 → 勝利
2. 相手がデッドライン(画面下 y=636)に触れる → 落下負け
3. ターン上限 → HP残存率の高い方が勝ち
4. **引き分け** … 両者同時撃破(決まり手「相討ち」)、またはターン上限でHP同率

引き分けの扱い: 連勝数は維持、ランキングへは送信しない、オンラインでも送受信可能。

#### ターンの流れ

```
手番開始
 → 燃料を満タンに戻す
 → (CPUなら移動計画を立てる)
 → 移動 / 照準
 → 発射
 → 着弾・落下が収まるまで待つ(0.8秒の余韻)
 → 移動不能デバフを1減らす
 → 必殺チャージ +1
 → 次の手番へ
```

#### 物理演算

- 重力 650 px/s²、風の最大加速度 260 px/s²、初速係数 7.8
- 弾はキャラごとの倍率(風耐性・重力耐性・初速)を掛けて飛ぶ
- 弾道プレビュー線あり。長さはキャラごとに異なる(恐竜が最長)

#### 風システム

- 全員が2巡するごとに切り替わる(1対1では4ターンごと)
- 切り替えのたび18%の確率で無風。対戦全体が無風になる確率6%
- 演習とオンラインでは固定風(左/右/無風)を選べる

#### 地形破壊

- ピクセルマスク方式。480列 × 4px刻みの格子で判定
- **1列に複数の区間を持てる**ため、洞窟・庇・浮島・空洞を表現できる
- 着弾で円形に削れる。削った履歴(`craterHistory`)を保存・同期している
- 地形パターンは7種類 + 闘技場(闘技場は 2/8 の確率で出現)
  - 左高台 / 右高台 / 中央山 / 中央谷 / 丘陵 / 大橋 / **闘技場**(三段棚+中央奈落+吊り下げ障害物)

#### CPU戦

- 精度は**連勝数だけ**で決まる4段階(弾道の誤差 38% → 20% → 9% → 2%)
- 理論上の正解弾道を逆算し、そこに誤差を乗せる方式
- 移動は「近すぎる(150px未満)」「遠すぎる(760px超)」時だけ
- 奈落へ自分から踏み込まない安全判定あり
- 10連勝ごとにボス戦(闘技場マップ固定・専用BGM・専用背景・バナー演出)

#### オンライン対戦

- Firebase Realtime Database(REST + SSE)
- 方式は「**行動側権威 + ターン境界スナップショット**」
- 部屋は8文字の合言葉(見間違えやすい I・O・1・0 を除外)。合言葉なしの「簡単対戦」枠もある
- 4席(p1ホスト / e1対戦者 / s1・s2観戦)
- キャラ選択はコミット&公開方式(先に選んだ方が不利にならない)
- 部屋の寿命10分、ホストが1分ごとに延命
- 再戦投票、観戦者へのスナップショット配信あり


#### 武器・スキルシステムについて

**存在しない。** 装備・習得・付け替えの概念はなく、
キャラ = ステータス + 必殺技1個 の固定セット。

状態異常は `moveLockTurns`(移動封印、0〜2ターン)の**1種類だけ**。

#### 必殺技の共通仕様

- 自分の手番4回でチャージ満タン
- 新規挑戦は0から。次戦へ残量を持ち越す
- 発動時にカットイン演出(顔アップ+技名)

#### 跳躍(v91の新機能・全キャラ共通)

- 1試合に1回だけ使用可能
- 専用の弾は出さず、**自キャラ自身を弾として飛ばす**
- 飛行中は元の位置のキャラを非表示にする
- 着弾地点へ移動。ダメージ・爆発・地形破壊はなし
- 移動不能デバフ中は使用不可
- **着地後、次の自分の1ターンは移動不能**
- 闘技場の垂直な壁や急角度の面には張り付かず落下する

### ④ プロジェクト構造

```
katamon/
├ index.html          ← ゲーム本体。これがすべて(10,558行)
├ sw.js               ← PWAキャッシュ(バージョン番号を index.html と揃える)
├ manifest.webmanifest
├ database.rules.json ← Firebaseのセキュリティルール(手でConsoleへ反映が必要)
├ assets/             ← キャラ16枚・背景5枚・BGM7曲・アイコン類
├ gas/ranking.gs      ← ランキングAPI(Google Apps Script)
├ tests/              ← ブラウザなしで動く検証ハーネス(7本)
├ docs/               ← モデル選択の詳細版・本文書
└ HANDOFF_*.md 他     ← 各時点の引き継ぎ書
```

#### 責務分割

`index.html` の中は `// ===== 見出し =====` で約50ブロックに区切られている。
主なもの: 地形生成 / ステージテーマ / キャラクター / ユニット / 席 / 風 / 弾道物理 /
花火 / デスゲート / ターン制御 / 中断・再開 / オンライン / CPU AI / 描画 / ミニマップ /
ランキング / オンラインロビー / サウンド設定 / 入力 / ゲームループ。

ファイルは1つだが、中身は整理されている。

#### 設計方針(コード内のコメントとテストから読み取れるもの)

- **推測で直さず、再現してから直す。** 再現コードがそのまま回帰テストになる
- **見た目も数値で検査する。** Canvasは自動で見られないので「画面内に収まる」「他の要素に
  被らない」を座標の関係としてテストに書く。この方式で実際に3件のバグを捕まえている
- **段階を切る。** 表示だけの変更を先に出し、ルール変更を後に回す。
  ルールを触った時に不具合が出れば原因が一意に決まる
- **検証フックは本体に入れない。** `tests/seatharness.js` が実行時に注入する

#### テスト(ブラウザ不要・依存なしで動く)

| ファイル | 内容 |
|---|---|
| `seattest.js` | 席の切り替え。入力・HUD・弾のowner・勝敗が席側を向いているか(20項目) |
| `regressiontest.js` | CPU戦の完走・中断再開のラウンドトリップ・演習(38項目) |
| `resulttest.js` | 結果画面の「タイトルへ戻る」 |
| `loopbacktest.js` | オンライン対戦。host/guestを別プロセスで動かし、遅延とロスを注入(93項目) |
| `stage3test.js` | Firebaseの部屋コード・SSE・commit/reveal・ルール文面・UI座標(209項目) |
| `lobbysimtest.js` | ロビーのコミット・公開を**メッセージの届く順を変えて**検証 |

### ⑤ オンライン

#### 同期方式: 行動側権威 + ターン境界スナップショット

- 撃った側が物理を回して着弾させ、ターンの切れ目に全状態(`buildSnapshot()`)を送る
- 受けた側は発射コマンドを再生して見た目を合わせ、届いたスナップショットで上書きする
- **これにより物理の決定性を諦めてよい設計になっている**
  (可変dt・非シードの地形生成のままで成立する)

#### 通信設計

- インターフェースは `send / onMessage / close` の3つだけ。開発時はBroadcastChannelに差し替え可能
- パケット種別:
  `lobbyState / settings / start / ready / move / fire / boom / state / result / bye /
   commit / reveal / rematchVote / presence / ping`
- 全パケットに プロトコル版数(v3)・送信者UID・自分の席・ラウンドID が必須
- クライアント側と `database.rules.json` の**両方**で検証(二重チェック)

#### 部屋システム

- 4席(p1 / e1 / s1 / s2)、8文字の合言葉、寿命10分・ホストが1分ごとに延命
- 期限切れの部屋は誰でも上書き作成できる
  → **乗っ取りの仕組みを新設せずに「放置された部屋が塞がる」問題を解決した設計**
- 合言葉なしの「簡単対戦」は固定部屋コードを1つ使い回す

#### 観戦

- s1 / s2 の2席
- `presence` / `ping` / `bye` 以外は書き込めない(サーバー側ルールで強制)
- 入室時に最新スナップショットを受け取る

#### 再戦

- 両者の投票で成立
- **ただしルールでは強制していない。** 投票はメッセージであって保存された状態ではないため、
  サーバー側からは「両者が投票済み」を判定できず、ホストは投票を待たずに次ラウンドを開ける

### ⑥ セーブデータ

localStorage に5つのキーを持つ。**サーバー側に個人アカウントはない。**

| キー | 内容 | 変更の影響 |
|---|---|---|
| `katamon_suspend_v1` | 中断した試合の全状態(スナップショット版数4) | 大きい。項目追加は4経路に波及 |
| `katamon_ranking_v1` | 端末ID・プレイヤー名・未送信スコア | 小さい |
| `katamon_audio_v1` | BGM/効果音の音量・ON/OFF | 小さい |
| `katamon_camera_zoom_v1` | 視点距離(v91で追加) | 小さい |
| `katamon_online_log_v1` | 通信の記録(最大80件・不具合調査用) | 小さい |

#### 中断セーブの中身

地形の生成データと破壊履歴、全ユニット(HP / 燃料 / 位置 / 必殺チャージ / 移動封印 /
跳躍の残り / 向き)、手番順・ターン数、風、連勝数、与ダメ効率、ボス戦フラグ、カメラ位置。

対人戦は片方だけ中断しても再開できないため保存しない。

#### ランキング(Google Apps Script + スプレッドシート)

- 列: `period / deviceId / name / streak / efficiency / updatedAt / character`
- 月間リセット、トップ20 + 自分の順位
- 順位は「連勝数が主・与ダメ効率が従」
- 送信は**連勝が途切れた瞬間だけ**。オンライン対人戦と演習は送らない
  (勝ちの譲り合いの温床になるため意図的に除外)
- 1台1日60回の上限、異常値の足切りあり

#### 今後追加できそうな項目

| 項目 | 追加コスト | 互換性への影響 |
|---|---|---|
| 対人戦の通算戦績(端末内) | 小 | 新キーを足すだけ。既存に影響なし |
| お気に入りキャラ・最後に使ったキャラ | 小 | 同上 |
| 中断セーブへの項目追加 | **大** | ①同期 ②パケット検証 ③再戦初期化 ④中断セーブ の4経路すべてに波及 |
| ランキングの列追加 | 中 | GASの再デプロイが必要。列は**末尾に足す**こと(既存行の意味が変わらない) |

## 現在できないこと

### ゲームとして無いもの

- 2対2 / 多人数戦(1対1のみ)
- キャラの成長・解放・アンロック。**全16体が最初から使える**
- 装備・アイテム・道具の切り替え
- 状態異常のバリエーション(移動封印1種類のみ)
- ストーリー・キャンペーン・ステージ進行
- CPUの難易度選択(連勝数に自動連動するのみ)
- リプレイ・観戦の巻き戻し
- 対戦部屋内での戦績表示
- タイトルの更新履歴表示

### オンラインで未対応

- **切断・画面ロックからの再入室**(Stage 4-3として未着手)。
  オンライン中は中断セーブを保存しないため、通信が切れたら試合は失われる
- 対人戦の戦績・レーティング。**オンラインの勝敗はどこにも記録されない**
- ランキングの同一プレイヤー3件までの制限(GAS再デプロイが必要)

### 既知の未確認・懸案事項

- **跳躍の壁への着地・落下は実機未確認。** 自動テストは通過しているが、
  Canvasの描画は自動検証できない
- **拡散弾(スモエルの花火)にバグの見込みがある。** 直し方は `IDEAS_必殺技.md` §2-2 に記載済み。
  実際の発生報告はまだ無いが、**拡散弾を使う技を増やす前に直す必要がある**
- HPバーが一瞬だけ見積もり値で動いてから正しい値に落ち着く(数字は修正済み、バーは未修正)
- 観戦席のゴースト(部屋が10分で切れるので影響は小さい)

## 流用できる仕組み

企画を考える時、**新規に作らなくても既にある部品**。

| 部品 | 何ができるか | コスト |
|---|---|---|
| `pierce` フラグ | 地形で消えずに進む貫通弾 | ほぼ0 |
| `spawnFireworkBurst()` | 着弾点からの拡散弾。発数・威力倍率も指定済み | ほぼ0 |
| `moveLockTurns` | **ターン数で切れる状態異常**。保存・同期・検証すべてに入っている | ほぼ0 |
| `emitEmp()` | 範囲に効果を撒く判定と演出 | ほぼ0 |
| `spawnLightningRemnant()` | 落雷の演出 | ほぼ0 |
| `spawnHealText()` | 回復の「+N」ポップ | ほぼ0 |
| `boom` パケット | **飛行中の弾を任意のタイミングで起爆できる**。ルールにも定義済み | ほぼ0 |
| クレーターの同期 | **地形破壊は毎ターン権威ある値で完全に揃う** | ほぼ0 |
| `damageTakenMul` | 被ダメージ軽減(現在は岩と騎士のみ使用) | ほぼ0 |
| 闘技場の外壁判定 | 画面上端より上でも壁が弾を止める | ほぼ0 |
| `deathGateMarker` の2段階技 | 「着弾で位置を決める → そこから別の効果が動き出す」型 | 小 |
| 跳躍の着地判定 | 「キャラを任意座標へ安全に移す」処理一式 | 小 |
| 浮島・洞窟の地形生成 | 1列に複数区間を持てるので、庇や空中足場が作れる | 小 |
| 吊り下げ障害物 | 揺れる遮蔽物。疑似乱数で毎試合同じ配置を復元できる | 小 |

**特に重要**: 地形の破壊履歴が同期されているため、**地形を削る技は当初の想定より安全**。
着弾位置が両端末で数pxズレても、毎ターンのスナップショットで地形ごと揃う。

## ボトルネック

### 1. `index.html` が単一ファイル(10,558行)

これは意図的な設計(ビルド不要・PWAで丸ごとキャッシュ)で利点も大きい。ただし:

- 複数の変更を同時に入れると差分が読めなくなる
- 別セッション・別モデルが同時に触ると衝突する
- **1回の作業 = 1つの変更**に切る運用でしか回らない

### 2. 必殺技のデータがコードの中に散っている

キャラのステータスは `CHARACTERS` の表にあるが、
**必殺技の効果は `launchShot()` の中の16分岐にべた書き**されている。

さらに初速倍率だけは表(`specialVelocityMul`)とコード(`vx0 * 2.15` など)の
**両方に同じ数字が書かれている**(表の方はCPUの照準計算専用)。

→ 必殺技を調整する時、2箇所を揃えて直す必要がある。
片方だけ直すとCPUだけ狙いが外れる。

### 3. 選択画面の★表示が実際の性能と連動していない

`selectStats: [耐久, 火力, 機動]` は手書きの数値で、`maxHp` や `blastMul` から
計算されていない。バランス調整をすると**表示と実性能がズレていく**。

### 4. CPUの照準が「重力と風を受ける単純な弾道」の逆算に限定されている

誘導弾・直進弾・多段発射はこの逆算が効かない。悪魔の必殺で既に例外を1つ手書きしている。

→ **CPUに使わせたい新技は、技ごとに照準処理を足す必要がある。**

### 5. Canvasの描画を自動検証できない

見た目の変更は必ず実機での目視確認が要る。
座標の関係(はみ出さない・被らない)はテストで押さえられるが、色・質感・演出は人が見るしかない。

### 6. 状態異常が移動封印1種類しかない

`moveLockTurns` は 0〜2 の範囲でスナップショット検証に固定されている。
「攻撃力ダウン」「継続ダメージ」などを足すには、状態異常を保持する仕組みごと設計が必要。

## 変更コストが高い箇所

### ★★★ 全面改修クラス

| 変更 | なぜ重いか |
|---|---|
| **リアルタイム制への変更** | 通信設計(ターン境界スナップショット)が根本から成立しなくなる。作り直し |
| **3人以上の同時対戦** | 席が4つ(うち2つは観戦)、ルールも4席前提。部屋・通信・勝敗判定すべてに波及 |
| **アカウント制・永続的な成長要素** | サーバー側に個人アカウントが無い。ランキングは端末ID方式で、端末を変えると別人になる |
| **状態異常の種類を増やす** | 保持・同期・検証・保存の4経路すべてに設計が要る |

### ★★ 慎重に進める必要がある

| 変更 | 注意点 |
|---|---|
| **新しいモンスターの追加** | `database.rules.json` がキャラのキーをべた書きで列挙しているため、**Firebase Consoleへ手で反映する一番重い手順**に乗る。ルールとクライアントは**必ず同時に上げる**(片方だけだとオンライン対戦が全滅する) |
| **スナップショットへの項目追加** | ①オンラインの同期 ②Firebaseパケット検証 ③再戦の初期化 ④中断セーブ の**4経路すべて**に効く。1つ忘れると、そこだけ復元されない不具合になる |
| **ランキングの仕様変更** | GASの再デプロイが必要(ユーザーのGoogleアカウントで手作業)。列は末尾に足すこと |
| **ダメージ計算の変更** | 過去に一度、帯固定へ変更して公平性を壊し、戻した経緯あり(v63 → v66)。**同じ失敗を繰り返さないこと** |
| **通信プロトコルの変更** | 全員が同時に更新できない前提。旧版の端末が混ざる |

### ★ 比較的安全

- 既存キャラの必殺技の効果変更(通信項目が増えない範囲)
- 地形パターン・ステージテーマの追加
- 表示・演出・UI配置の調整
- CPUの行動ロジック調整

## 将来企画を考える際に知っておくべきこと

### 1. この設計の一番の強みは「地形」と「通信」

地形は1列に複数区間を持てる本格的なマスク方式で、洞窟・庇・浮島・吊り下げ障害物まで
表現できている。しかも**破壊履歴が完全に同期される**。
地形を使った企画は、見た目の印象よりずっと安く作れる。

通信は「行動側権威 + ターン境界スナップショット」で、演出のズレを許容する設計。
**ターン制であることがこの設計を成立させている。**
ターン制を捨てる企画は、通信の作り直しを意味する。

### 2. 一番の弱点は「1試合が単発で終わること」

現在、試合を跨いで残るのは **連勝数・与ダメ効率・必殺チャージの残量** だけ。
しかもオンライン対人戦は連勝にもランキングにも含めない
(勝ちの譲り合いを防ぐため意図的にそうしてある)。

つまり**友人同士で対戦しても、何も積み上がらない。**
5〜10人で長く遊ぶという目的に対して、ここが構造的な空白になっている。

課金・ガチャ・スタミナ・ログインボーナスを入れないという方針は、
この空白を「毎日やる理由」で埋めない、という選択でもある。何で埋めるかは企画の中心論点。

### 3. 「1機能を足す」の実コストは、通信に触れるかどうかで10倍違う

- 通信項目が**増えない**変更 … `index.html` だけ。テストを流して終わり
- 通信項目が**増える**変更 … `index.html` + `database.rules.json` + テスト3種
  + **Firebase Consoleへ手で反映**

企画を評価する時、「これは通信項目が増えるか?」を最初に確認するのが一番効く。

### 4. モンスターを増やすのは、見た目より高い

キャラ定義は1行だが、①画像1枚の用意 ②必殺技の実装 ③CPUの照準対応
④`database.rules.json` の再デプロイ が付いてくる。

**既存16体に技を足す方が、17体目を作るより安い。**

### 5. ターン制だからこそ安く作れるもの

「Nターン後に発動する」「次の手番まで持続する」といった時限式の仕組みは、
`moveLockTurns` と同じ型でほぼ無料で作れる。
逆に「同時に動く」「リアルタイムで判定する」ものは高い。

### 6. CPU戦と対人戦は、実質べつのゲームになっている

- **CPU戦**: 連勝を積む → 途切れたらランキングへ送信 → 10連勝ごとにボス戦
- **対人戦**: 連勝もランキングも無関係。1試合ごとに完結

この非対称は意図的なものだが、企画がどちらを対象にしているかで使える仕組みが変わる。

### 7. 実機確認が必須の領域がある

見た目・手触り・演出は自動検証できない。
企画を評価する時、「実装後に人が確認する量」も判断材料になる。

### 8. 既にアイデアが整理済みの領域がある

`IDEAS_必殺技.md` に必殺技のアイデア10件と着手順の提案がまとまっている。
企画レビューがこれと重複した場合、**既に検討済みである点を踏まえた比較**が必要。
