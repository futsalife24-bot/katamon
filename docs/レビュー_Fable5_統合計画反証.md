## 1. 総評

**条件付き承認。**

統合計画は、3者レビューの対立点を実コードへ照合して裁いており、採否の大枠は妥当である。特に次の3点は反証を試みたが覆せなかった。

- ゲームプレイ用ロードアウトの却下（後述のとおり、緩和条件だけ1点残すべき）
- 物理再計算リプレイの却下とイベントテープ方式の採用
- ランダムイベントの却下

一方で、承認の条件とすべき問題が3つある。

1. **ボスラッシュの初回リリースが「ステータス盛りの連戦」になる構造**になっており、Fable 5レビューの核心（ボス＝ルールを1つ破る存在）が「構造だけ作る」へ後退している。初回に最低1体、ルール破りボスを含めること。
2. **クラッチ称号と直前ショットリプレイが、依存関係上の必然なく後ろへ送られている。** 「悔しさ三点セット」（因縁記録・傷跡・リプレイ）の完成がv117までずれ込む。優先順位の修正を提案する（§3）。
3. **因縁記録の相手キー（席UIDの永続性）が未確定のまま実装計画に入っている。** ここが割れると因縁の積み上げという目的自体が壊れるため、実装前に確定すること（§5-1）。

## 2. 採否判断の修正提案

採用・保留・却下の判断そのものへの修正は **1件のみ**。それ以外は現判断を支持する。

### 2-1. ロードアウト却下の「再検討しない」を条件付きへ緩和する

- **現在の判断**: 能力・パッシブ・必殺ロードアウトは却下。§9で「再検討しない。キャラ固有性と装備厳選禁止に反する」。
- **問題点**: 必殺技差し替えの却下は全面的に支持する（`launchShot()`・CPU照準・`applyCharacter()`への密結合は実コードで確認でき、キャラ固有性の毀損というデザイン上の理由も変わらない）。ただし「再検討しない」は一段広すぎる。前回Fable 5レビューの段階2「照準・移動系パッシブ1枠」（ガイド長+、跳躍後の移動不能なし等）は、ダメージ計算とHP・燃料に触れない限りOpus 5が警告した`applyCharacter()`の性能上書き問題を踏まず、CPU照準にも影響しない。さらに見た目カスタム（v119〜）がcommit/reveal・Snapshot・Firebaseルールの「装着IDを同期する配管」をまるごと建設するため、その後の限界費用は小さい。
- **変更すべき判断**: 却下は維持しつつ、§9の再検討条件を「再検討しない」から「見た目カスタムとキャリアカードを運用した後、自分らしさの表現が見た目だけでは不足だと実際のプレイで確認された場合に限り、ダメージ計算・HP・燃料へ一切触れない照準・移動系パッシブ1枠（全て無料・サイドグレード）のみ再検討する」へ変更する。
- **改善する体験**: 「自分らしい工夫の余地」への出口を完全封鎖しない。5〜10人の固定メンバーでは、見た目＋キャラ選択だけで個性が飽和する可能性があり、その時の逃げ道を残す。
- **代わりに失うもの**: 「二度と議論しない」という判断の確定性。装備厳選への滑り坂リスクはゼロにはならない（ただし1枠・サイドグレード限定で抑止できる）。

### 2-2. その他の採否

修正なし。特に以下は反証を試みた上で現判断を支持する。

- **リプレイのイベントテープ縮小**: 「名場面を残す」目的に対し、実戦中に描画された軌跡・爆発をそのまま再生する方式は、物理再計算より劣化がない。見返す名場面とは「実際に画面で起きたこと」であり、再計算による理論値再現ではない。Opus 5の非決定性指摘（可変`dt`・未シード乱数）は実コードで裏が取れており、この縮小は目的を失っていない。永続保存・共有の却下も、友人が隣にいるかDiscordで画面共有できる距離感なら端末内1回再生で足りる。
- **戦場の傷跡・固定シード・風予報・クラッチ称号**: 前回レビューの意図（因縁の積み上げ、同条件の話題、読み合いの深化）がそのまま採用されている。
- **少人数協力レイド・リーグ・宣言ショットの保留、ランダムイベントの却下**: 妥当。

## 3. 優先順位の修正提案

### 3-1. 残タスク1〜7の先行

**支持する。** 未検証の土台に新機能を積まない原則と、boom同期・Stage 4-3が複数の新企画の前提であることから、順序は正しい。

ただし1点。残5（GASランキング改修）と残6（席リースのゴースト対策）は、GAS再デプロイ・Firebase Console反映という**ユーザー側の手作業待ちで停滞しうる**。停滞した場合に限り、通信へ一切触れないキャリアカード（現v101）を先に差し込むことを許容する運用にすべきである。直列を硬直させて開発が止まるのが一番の損失。

### 3-2. 新企画の順序変更

- **現在順**: キャリアカード → カスタムルール → 傷跡 → ボスラッシュ → 固定シード → 風予報 → リプレイ → クラッチ称号 → 見た目カスタム
- **変更後**:

| 順 | Version | 内容 | 変更 |
|---:|---|---|---|
| 8 | v101 | キャリアカード | 変更なし |
| 9 | v102 | クラッチ称号 | **15→9へ前倒し** |
| 10 | v103〜v105 | プリセット型カスタムルール | 1つ後ろへ |
| 11 | v106〜v107 | 戦場の傷跡 | 1つ後ろへ |
| 12 | v108〜v110 | 直前ショットリプレイ | **14→12へ前倒し** |
| 13 | v111〜v112 | 次回の風予報 | 変更なし相当 |
| 14 | v113〜v115 | ボスラッシュ | **11→14へ後退** |
| 15 | v116〜v118 | 固定シードチャレンジ | **12→15へ後退** |
| 16 | v119〜v121 | 見た目カスタム | 変更なし |

- **理由**:
  1. **クラッチ称号（現15位）は依存も規模も後回しの理由がない。** 依存は端末内戦績（残4、v95完了）だけで、規模は小（1版）、通信・Console作業なし。現計画では依存完了から23版後になる。戦績直後に置けば、v102時点で「因縁記録＋称号」が揃い、負けた側がもう1戦押す燃料が最速で入る。
  2. **リプレイ（現14位）の前提はboom同期（v92完了）だけ。** ローカル完結・通信副作用なしにもかかわらず、計画自身が面白さ5点を付けた機能がv115まで待つのは、計画の判断基準（面白さ最優先）と矛盾する。前回レビューの「悔しさ三点セット」（因縁・傷跡・リプレイ）の完成が、現在順のv117から**v110へ7版早まる**。
  3. **ボスラッシュと固定シードは後退させる。** どちらもソロ・ローカル機能であり、対象読者（5〜10人の友人がオンラインで殴り合う）のコアループへの寄与は、三点セットとカスタムルールより一段劣る。またボスラッシュは§4-3の修正（初回にルール破りボス1体）で設計時間が要るため、後ろの枠の方が収まりがよい。
  4. カスタムルール→傷跡→風予報を連続させることで、Snapshot版数上げとFirebase Console反映を要する作業が1つの塊になり、Opus 5の「ルール変更はまとめて反映」という運用指針とも整合する。
- **代わりに失うもの**: ボスラッシュ（面白さ5点）が約6版、固定シードが約6版遅れる。ソロの柱の充実を急ぎたい場合はこの変更を採らない選択もあるが、その場合もクラッチ称号の前倒し（理由1）だけは採るべきである。

## 4. 機能別の反証結果

| 機能 | 判定 | 内容 |
|---|---|---|
| 端末内戦績・因縁 | **軽微修正** | 設計は良い。ただし相手キーに使う「席UID」の永続性が未確定（§5-1）。匿名認証UIDが端末単位なら、友人が機種変更・再インストールした瞬間に因縁が分断され、「あいつに12勝14敗」という積み上げの核が壊れる。実装前に確定必須 |
| キャリアカード | 問題なし | 全キャラ最初から閲覧・戦績0件耐性・収集要素なし、いずれも前回レビューの意図どおり |
| プリセット型カスタムルール | **軽微修正** | 値域固定プリセットからの開始は支持。ただし前回レビューの核心だった**「名前を付けて呼べるハウスルール」の社会的機能**（「今日は例のアレで」）が消えている。同梱プリセットに名前を付ける、または許可値の組合せへ端末内で名前を保存できるようにする（許可値の組合せに解決されるだけなので同期・検証面は増えない）。§5-3も参照 |
| 戦場の傷跡 | **軽微修正** | 開始不能時の新地形フォールバックは正しい。ただし「何連戦まで持ち越すか・どうリセットするか」と「岩盤下限（これ以上削れないライン）を入れるか」が未確定（§5-4）。前回レビューでも下限は要検討と明記した点で、計画から落ちている |
| ボスラッシュ | **重大修正** | §4-3参照。初回リリースが「HP補正＋AI精度」のみの構成になる計画で、Fable 5が採用理由とした体験（ルール破りの攻略パズル）が初回に1つも入らない |
| 固定シードチャレンジ | **軽微修正** | 「全員が同じCPU判断で開始する」という記述は誤解を生む。シード乱数でもCPUの消費順はプレイヤーの操作に依存するため、**同一なのは初期地形・風系列・敵構成までで、展開は操作次第で変わる**。ここを仕様として明示しないと「俺のCPUは違う動きをした」という揉め事になる（§5-6）。乱数ストリームは地形・風・CPUで分離し、少なくとも風系列は操作に依らず同一にすべき |
| 次回の風予報 | 問題なし | 予報値を必ず消費し再抽選しない設計は正しい。読み合いの深化という前回の意図をそのまま実現する。適用範囲だけ§5-7で確定 |
| 直前ショットリプレイ | **軽微修正** | イベントテープ方式・端末内・次戦破棄はすべて支持。ただし再生の起動方式（自動か手動か）と長さが未確定で、これはテンポ（変更不可の軸）に直結する（§5-5）。boom同期の前提条件化も、リプレイがv92より後にある限り実害なく妥当 |
| クラッチ称号 | 問題なし | データ定義に閉じ、報酬化しない設計は正しい。順序のみ§3で修正 |
| 見た目カスタム | 問題なし | 全項目無料・解放なし・性能不変で、装備厳選の禁止と両立している。MVPを削るなら紋章より「カラー＋弾軌跡」から始めると3版を2版へ圧縮できるが、必須ではない |

### 4-3. ボスラッシュの重大修正（詳細）

- **現在の計画**: 「ボス固有の『ルールを1つ破る』挙動は、1ボス1変更・1Issueで追加できる構造だけ先に作る」。初回のボス定義はキャラ・地形・風・HP補正・AI精度の組合せ。
- **問題**: 実コード確認のとおり、現行の`isBossMatch`は演出フラグであり、ボスの中身は通常CPUと同じである。初回リリースが「HPが多く照準が正確なCPUの連戦」だと、それは既存連勝モードの再包装であり、友人グループは一度触って「薄い」と判断したら戻ってこない。**初回の印象を演出とステータスだけで作るのは、この機能の採用理由（面白さ5点）を初回に放棄することに等しい。**
- **修正案**: 初回リリース（連戦3〜5体想定）に、最低1体のルール破りボスを含める。候補は前回レビュー2-2の中から、CPU照準の追加実装が不要なものを選ぶ。
  - **岩盤持ち**（自分の周囲の地形が削れない）: 照準に影響なし。`carveCrater()`側のガード1つ
  - **1手番2回撃つ**: 既存照準をそのまま2回呼ぶ
  - **風を自分有利へ固定**: 風は照準計算に織込み済みで、固定風の仕組みも既存
  - 「巨大で直撃判定が大きい代わりに移動しない」も安いが、上記より演出対応が要る
- **失うもの**: 初回リリースの実装量がボス1体分増える（構造＋定義1件なので、増分は1Issue相当）。

## 5. 実装前に決めるべき未確定事項（優先順・7件）

1. **因縁記録の相手キーの永続性**（戦績・v94着手前）
   席UID（匿名認証）が端末単位か否かを確認し、友人の機種変更・再インストール・複数端末で因縁が分断/二重化した場合の扱い（別人として表示するか、表示名で束ねる導線を出すか）を決める。ここが曖昧だと「俺の12勝が消えた」という一番揉める事故になる。
2. **ボスラッシュの敗北・再挑戦仕様と初回のルール破りボス1体**（v113着手前、設計は早めに）
   敗北時に最初からか当該ボスからか、HP・必殺チャージを連戦間で持ち越すか、を決める。`resetMatch(carrySpecialCharge)`が既にあるため両方作れてしまい、決めずに着手すると手戻りする。あわせて§4-3の初回ボスを選定する。
3. **カスタムルールの具体的なプリセット表**（v103着手前）
   各軸（重力・HP・燃料・チャージ・爆風）の許可値と、同梱する名前付きプリセット1〜2個（例: 低重力・爆風2倍のカオス系）を表で確定する。「テンポを損なう極端値」の線引き（例: 1試合が2分を超える組合せは不許可）もここで決める。
4. **戦場の傷跡の終了条件**（v106着手前）
   持ち越しは何連戦まで続くのか（無制限か、n戦で新地形か、部屋設定で切替か）、岩盤下限を入れるか、を決める。連戦の後半が「落とし合い」へ変質するのは狙いどおりだが、終わらせ方を決めないと「もう地形がないからやめよう」で部屋が解散する。
5. **リプレイの再生仕様**（v108着手前）
   結果画面から手動起動か決着直後に自動再生か、再生秒数の上限（テンポ許容は再戦導線を塞がない5〜8秒程度を推奨）、時間切れ・場外落下・引き分け決着時に何を再生するか（最後の発射か、再生なしか）を決める。
6. **固定シードチャレンジの「同条件」の範囲とスコア**（v116着手前）
   同一保証は初期地形・風系列・敵構成までで、CPUの実際の動きは操作に依存して変わることを課題画面に明記する。比較するスコア指標（残HP・ターン数・与ダメ効率のどれか）と、端末内ベスト記録の持ち方を決める。
7. **風予報の適用範囲**（v111着手前）
   常時ONか、カスタムルール・チャレンジ側で無効化できるか。予報なしの緊張感を好む場合の逃げ道と、チャレンジ課題（「次の風を待つ」系の課題設計）との整合をここで確定する。

## 6. 統合計画へ反映すべき具体的な文章修正

### 6-1. §6.5 ボスラッシュ「採用範囲」

- **現在の問題**: 「ボス固有の『ルールを1つ破る』挙動は、〜構造だけ先に作る」により、初回がステータス連戦になる。
- **差し替え案**:
  > ボス固有の「ルールを1つ破る」挙動は、1ボス1変更・1Issueで追加できるデータ構造として実装し、**初回リリースに最低1体、ルール破りボスを含める**。初回の候補は、CPU照準へ追加実装が不要な「周囲の地形が削れない岩盤持ち」「1手番に2回撃つ」「風を自分有利へ固定」から選ぶ。HP補正とAI精度だけのボスは、ルール破りボスの間を埋める脇役とし、初回の目玉にしない。

### 6-2. §9 保留・却下案の再検討条件（ロードアウト行）

- **現在の問題**: 「再検討しない」が、前回Fable 5レビューの段階2（パッシブ1枠）まで恒久封鎖している。
- **差し替え案**:
  > | 能力・パッシブ・必殺ロードアウト | 却下 | 必殺・能力の差し替えは再検討しない。キャラ固有性と装備厳選禁止に反する。ただし見た目カスタムとキャリアカードの運用後、見た目だけでは自分らしさが不足すると実プレイで確認された場合に限り、ダメージ計算・HP・燃料へ一切触れない照準・移動系パッシブ1枠（全て無料・サイドグレード限定）のみ再検討してよい |

### 6-3. §6.3 プリセット型カスタムルール「採用範囲」

- **現在の問題**: ハウスルールを「名前で呼べる」社会的機能が落ちている。
- **差し替え案**（末尾へ追記）:
  > 同梱プリセットには固有の名前を付け、許可値の組合せへ端末内で名前を保存できるようにする。保存されるのは許可値の組合せへの参照だけであり、同期・検証の対象は増やさない。「今日は例のアレで」と呼び合える状態を採用範囲に含める。

### 6-4. §6.1 端末内戦績・因縁記録「採用範囲」

- **現在の問題**: 相手キーの永続性が未確定のまま「席UIDを優先」とだけ書かれている。
- **差し替え案**（保存先の段落へ追記）:
  > 着手前に、席UIDが端末をまたいで安定するかを確認し、機種変更・再インストール・複数端末で記録が分断した場合の扱い（別記録として表示するか、表示名で束ねる導線を出すか）を確定してから実装する。

### 6-5. §6.6 固定シードチャレンジ「採用範囲」

- **現在の問題**: 「同じキャラ、地形、風、CPU判断で開始する」が、CPU挙動まで全員同一と読める。
- **差し替え案**:
  > 同じ日付・同じ課題なら、初期地形、風系列、敵構成が全員同一になるローカル課題。CPUの実際の行動はプレイヤーの操作に応じて変わるため、同一保証は初期条件と風系列までであることを課題画面に明記する。乱数ストリームは地形・風・CPUで分離し、風系列は操作に依存させない。

### 6-6. §7 Versionロードマップ

- **現在の問題**: クラッチ称号とリプレイが依存関係上の必然なく後置され、「悔しさ三点セット」の完成がv117になる。
