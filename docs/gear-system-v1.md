# CATAMON PROJECT「ギア」システム統合仕様 v1.0

- 作成日: 2026-08-25
- 企画正本: 本チャットのQ1〜Q280で確定した内容
- GitHub確認時点: `futsalife24-bot/katamon` `master` / `3812d682b94386d1677d025b9e3a4f34d79fff18`
- 現行公開版: v2.0.142（BATTLE / GARAGE 2ページ化済み）
- 方針: **仕様は全体を正本として残し、実装は段階分割する**

---

## 0. 目的

カタモンへ、陰陽師の「御魂」やサマナーズウォーの「ルーン」に近い装備ハクスラを追加する。

中心となる循環は次のとおり。

1. 協力ボスまたはCPU BATTLEを遊ぶ
2. ランダムなギアを獲得する
3. セット・部位・★・レア度・メインOP・サブOPを選別する
4. `+3 / +6 / +9 / +12`で強化結果を見る
5. 当たりは装備、外れは分解
6. 粉末で強化し、設計片で指定箱を制作
7. 新しいビルドで高難度や対戦へ挑む

### 設計原則

- スマホ縦画面を正本にする
- 想定ユーザーは友人中心で、長時間周回を強制しない
- ドロップはランダムでも、外れが強化・制作資源へ変わる
- ギア性能は全モードで有効
- 砲撃精度・位置取り・判断が主役であり、ギアだけで勝敗を決めない
- 付け替え作業、整理地獄、報酬消失を避ける
- 強化成功率ではなく「サブOPの追加・伸び先」をガチャの中心にする
- ギア関連素材は起動時へ一斉投入せず、少数の再利用可能パーツへ分解し、タイトル・GARAGEのアイドル時間に段階的に取得・デコードする

# 1. 所有・装備・プリセット

## 1.1 所有方式

- ギアはプレイヤー共通倉庫で所有する
- 全ギアを全カタモンが装備可能
- キャラタイプ・重量・属性などによる装備制限は設けない
- ギアは実物1個として扱う

## 1.2 プリセット

- 1カタモンにつき3プリセット
- プリセット名は変更可能
- モードごとの既定プリセットを設定可能
  - 例: 通常対戦 → Preset 2
  - 協力ボス → Preset 3
- モード選択時に自動選択するが、出撃確定前なら手動変更可能
- 付け替え・プリセット変更は無料
- マッチ開始時に装備をスナップショットし、戦闘中は変更不可

## 1.3 共有登録と競合

- 同じ実物ギアを複数カタモンのプリセットへ登録可能
- 出撃カタモンを選んだ時に自動付け替え
- 同一プレイヤーが複数カタモンを同時出撃させる際、同じ実物ギアが競合した場合は出撃不可
- 競合ギアと対象カタモンを明示し、差し替えを求める
- ゲーム側で勝手に代替装備へ変更しない

# 2. 6部位

配置は固定し、プレイヤーが位置で覚えられるようにする。

| 部位 | 種別 | メインOP |
|---|---|---|
| 砲身 | 固定 | 攻撃＋固定値 |
| 装甲 | 固定 | HP＋固定値 |
| コア | 固定 | 防御＋固定値 |
| 動力 | 可変 | 攻撃% / HP% / 防御% / 最大燃料 / ノックバック威力 / ノックバック耐性 |
| 照準 | 可変 | 攻撃% / HP% / 防御% / 会心率 / 会心ダメージ |
| 補助機構 | 可変 | 攻撃% / HP% / 防御% / 爆風威力 / 状態異常耐性 / 回復効果 / シールド効果 |

### 固定部位

- 固定値メインは`+1〜+12`で毎レベルほぼ均等に成長
- ★6・+12で、標準的なカタモンの対応基礎値に対して概ね10〜15%相当を初期目安にする
- 正確な固定値は現行キャラクターカタログの攻撃・HP・防御分布を調査して逆算
- 固定3部位の★差は可変3部位より小さくする

#### v1固定メイン較正（承認済み）

上の方針を残したうえで、砲身・装甲・コアのギア内メイン値は、v1では同じ完成値テーブルを用いる。
これは**ギア数値・GS分母の共通基準**である。`Normalized 100`はギア側のAttack/Defense互換参照であり、現行戦闘へ新しい基礎値を導入するものではない。

| ★ | 砲身 攻撃+ | 装甲 HP+ | コア 防御+ | +0値 |
|---|---:|---:|---:|---:|
| ★1 | 4 | 4 | 4 | 1 |
| ★2 | 5 | 5 | 5 | 1 |
| ★3 | 7 | 7 | 7 | 1 |
| ★4 | 9 | 9 | 9 | 2 |
| ★5 | 10 | 10 | 10 | 2 |
| ★6 | 12 | 12 | 12 | 3 |

- `+0`は完成値の25%を切り捨て、残りを`+1〜+12`へ整数のまま配分する。`+12`では必ず表の完成値へ一致する。
- 現行の通常カタモン18体のHPは**66〜140、平均99.11、中央値96.5、Q1=84、Q3=110、両端除外平均98.625**。装甲★6・+12の`HP+12`は、平均に対して約12.1%、中央値に対して約12.4%で、旧方針の「概ね10〜15%」の較正根拠になる。最小66には約18.2%、最大140には約8.6%となるため、実戦の影響は戦闘式確定後に再測定する。
- 攻撃・防御は現行で共通の基礎値・最終式・丸め順が未確定である。固定表をそのままダメージまたは軽減へ接続せず、**最終Attack/Defense式と丸め規則はPhase 3で決定する**。
- 可変3部位の`+28%`メイン、13種サブOP、セット効果を同時に積むと、固定値より割合値の累積が支配的になるリスクがある。実戦差20〜30%の確認と必要な上限調整は、Phase 3の代表ビルド検証で行う。

### 可変部位

可変メインの`+12`完成値は、初期版では全種類共通テーブルを使う。

| ★ | +12完成値 |
|---|---:|
| ★1 | +8% |
| ★2 | +12% |
| ★3 | +16% |
| ★4 | +20% |
| ★5 | +24% |
| ★6 | +28% |

### +0時の補完仕様

Q1〜Q280では+0時のメイン値が未確定だったため、初期実装の補完値を次とする。

- `+0 = +12完成値の25%`
- 残り75%を`+1〜+12`へほぼ均等配分
- 端数は表示単位に合わせて調整し、+12で完成値へ一致させる
- この比率は`BALANCE_TUNING`へ集約する

## 3.1 全6部位共通13種類

1. 攻撃%
2. HP%
3. 防御%
4. 会心率
5. 会心ダメージ
6. 爆風威力
7. ノックバック威力
8. ノックバック耐性
9. 状態異常耐性
10. 回復効果
11. 被回復効果
12. シールド効果
13. 被シールド効果

### ルール

- 固定値サブOPは採用しない
- 13種類は全6部位で同確率
- 部位・セット・メインOPによる出現率優遇はしない
- 1個のギア内で同じサブOPを2枠以上持たない
- メインOPと同種のサブOPは付与可能
- 同じサブOPへ強化が複数回入ることは可能
- サブOPごとに、強化が入った回数を表示
  - 例: `会心率 +31%〔+4〕`

## 3.2 ★別の初期値・1回強化幅

全13種類で共通。

| ★ | 1回の抽選幅 |
|---|---:|
| ★1 | 1〜2% |
| ★2 | 1〜3% |
| ★3 | 2〜4% |
| ★4 | 3〜5% |
| ★5 | 4〜6% |
| ★6 | 5〜7% |

# 5. 強化

## 5.1 基本

- 最大`+12`
- 強化失敗なし
- メインOPは毎レベル上昇
- `+3 / +6 / +9 / +12`でサブ抽選
- サブが4個未満なら、新しいサブOPを追加
- 4個揃った後は、4つから完全等確率25%で1つを強化
- 同じOPへ連続で入ることを抑制しない
- 初期値・強化幅は毎回、該当★の範囲内でランダム

## 5.2 deterministic Seed

- ギア生成時に`enhancementSeed`を確定
- `+3 / +6 / +9 / +12`の未来結果をSeedから再現可能にする
- バックアップ復元、アプリ再起動、同じギアの再強化でも結果は変わらない
- 本番UIではSeedと未来結果を表示しない
- 開発モードだけ未来の強化結果を確認可能
- ギアIDごとに「どの段階まで結果を確認したか」をバックアップ対象外の端末履歴へ保存
- 同一端末での`強化→結果確認→古いバックアップ復元`による無料鑑定を防ぐ
- 別端末を利用した巻き戻しまでは初期版では対策しない

## 5.3 アトミック処理

- 強化ボタン押下時点で、コイン・粉末消費、全抽選結果、最終強化値を先に確定保存
- 演出は保存後に再生するだけ
- 演出中に終了した場合、次回起動時に未表示の節目だけ再演出

## 5.4 操作

- `+3まで / +6まで / +9まで / +12まで`の節目強化
- 複数節目をまたいでも、結果は節目順に表示
- 演出はタップで即スキップ可能
- 一括強化は最大10個
- 一括処理開始時に全件確定保存
- 途中で「残りをまとめて表示」へ切替可能
- 未処理分だけのキャンセルは不可
- 結果一覧からロック・お気に入り・分解候補選択が可能

# 6. 初期8セット

初期8種はすべて`2セット効果＋4セット効果`。

| セット | 2セット | 4セット |
|---|---|---|
| 猛攻 | 攻撃+8% | 砲弾を直接命中させた時、与ダメージ+12% |
| 生命 | HP+10% | 戦闘開始時、最大HPの8%分のシールド |
| 堅守 | 防御+10% | 砲弾を直接受けた時、被ダメージ-12% |
| 会心 | 会心率+8% | 会心ダメージ+20% |
| 爆砕 | 爆風威力+8% | 爆風範囲+8% |
| 衝撃 | ノックバック威力+10% | さらにノックバック威力+10%＋ノックバック耐性+10% |
| 救援 | 回復効果+8%＋シールド効果+8% | 自分以外の味方を実回復または実シールドした時、対象の次の攻撃+10% |
| 背水 | HP50%以下で攻撃+10% | 相手の攻撃アクションで実ダメージを受けた後、次の攻撃+10%。被弾後HP50%以下なら+15% |

## 6.1 共通セットルール

- 4個装備時は2セット効果と4セット効果の両方を発動
- 基本構成は`4+2`または`2+2+2`
- 同一セットを6個装備しても、2・4効果は各1回
- 初期版では6セット追加効果なし
- 将来、2個専用・4個専用・6個専用を追加可能
- セット効果はマッチ開始時に確定し、初期版では戦闘中に再計算しない

## 6.2 効果の細則

### 戦闘開始時

- 1試合につき最初の1回
- 協力ボスのラウンド切替では再発動しない

### 直撃

- 現行戦闘側の直接命中判定を流用
- 判定が存在しない箇所のみ「砲弾本体が対象へ接触してから爆発」を直撃として新設

### 救援

- 自己回復・自己シールドでは4セット効果を発動しない
- 回復は実回復量1以上
- シールドは実シールド増加量1以上
- 空回復・上限到達で増えなかったシールドでは発動しない

### 背水

- 砲弾直撃・爆風など、相手の攻撃アクションによる実ダメージで発動
- 毒・炎上等の継続ダメージ、環境ダメージでは発動しない
- HP50%判定は被弾後
- 同じ背水バフは加算せず上書き
- 通常+10%、被弾後HP50%以下なら+15%

### 次の攻撃バフ

- 同じソースの再付与は加算せず上書き
- 別セット由来なら加算可能
  - 例: 救援+10%＋背水+15%＝+25%
- 攻撃アクション全体を1単位として補正し、攻撃終了時に消費
- 多段・複数弾でも総攻撃アクションへ1回の倍率として適用

# 7. 戦闘ステータス・計算

## 7.1 会心

- 全カタモンの基礎会心率: 0%
- 基礎会心ダメージ: 150%
- 会心対象:
  - 砲弾直撃
  - 通常爆風ダメージ
- 会心対象外:
  - 毒・炎上等の継続ダメージ
  - 固定ダメージ
  - 回復

## 7.2 状態異常

- 状態異常命中ステータスは実装しない
- 状態異常技が命中した時の基礎付与率は原則100%
- `最終付与率 = 100% - 実効状態異常耐性`
- 通常の状態異常は共通耐性1種類
- 協力ボス専用ギミック・特殊状態は耐性対象外に設定可能

## 7.3 通常ステータスの加算

`攻撃% / HP% / 防御%`は、メイン・サブ・セットをすべて加算して基礎値へ1回だけ適用。

例:

`動力メイン12% + サブ18% + 猛攻8% = 攻撃+38%`

## 7.4 与ダメージ補正

- 直撃・ボス特効・HP条件など、同じ「与ダメージ補正」カテゴリ内は加算
- 合計を最後に1回乗算
- 会心倍率とは別乗算

例:

`基礎100 × 与ダメ1.12 × 会心1.5 = 168`

## 7.5 防御・軽減・シールド順

1. 攻撃計算
2. 既存の防御計算
3. 被ダメージ軽減
4. シールド
5. HP

- 被ダメ軽減は条件を問わず同一カテゴリへ加算
- 最終被ダメ軽減は最大40%
- 堅守4セットの直撃-12%も40%枠へ含む
- シールドは軽減後ダメージを受ける追加HP扱い

## 7.6 シールド

- 別ソースのシールドは加算
- 総シールド上限は最大HPの35%
- 上限未満なら空いている量だけ補充
- 超過分は切り捨て
- 既存シールドを上書きして損させない

## 7.7 ソフトキャップ

超過分は50%効率。

| 能力 | 等倍域 |
|---|---:|
| 会心率 | 70%まで |
| 会心ダメージ | 200%まで |
| 状態異常耐性 | 50%まで |
| 爆風威力 | +50%まで |
| 回復効果 | +70%まで |
| シールド効果 | +70%まで |
| 被回復効果 | +50%まで |
| 被シールド効果 | +50%まで |

キャップなし:

- 攻撃%
- HP%
- 防御%
- 最大燃料
- ノックバック威力
- ノックバック耐性

### UI表示

- 通常域: 通常色
- ソフトキャップ超過: 実効値を黄色
- ハードキャップ到達: 実効値を赤
- `装備値 → 実効値`を表示
- 詳細説明はギアガイドへ集約

## 7.8 全モード適用

- 協力ボス
- CPU BATTLE
- 通常オンライン対戦
- カスタム戦
- その他PvE

すべてでプレイヤーのギアを有効化する。

初期版ではCPUキャラクターや協力ボスへギアを持たせない。プレイヤー側の成長によってCPU連勝やボス攻略が進みやすくなることを、育成成果として許容する。

# 8. 戦力差の設計目標

Q12の「理想ギアと無装備で20〜30%程度」と、その後に確定したメイン・サブ数値を単純合算すると、理論上の神個体は20〜30%を超える可能性が高い。

このためv1では次の意味に統一する。

- **20〜30%は、現実的に到達する★5〜6・エピック〜レジェンド・+9〜12の整ったビルドと無装備の標準的な実戦差の目標**
- ★6ミシック・4跳ねを揃えた理論上の神ビルドは目標を超えてよい
- ただし対人で一撃決着や行動不能一強にならないこと
- 数値はすべて`BALANCE_TUNING`へ集約
- 本番有効化前に代表ビルドのシミュレーションと実戦テストを行う
- 隠れた全体倍率は安易に追加せず、メイン完成値・サブ幅・セット数値を明示的に調整する

# 12. ギア関連アセット・ロード・UI描画方針

## 12.0 適用範囲

本章が規定するのは、**ギアシステムv1で新規追加するアセット**と、そのロード・デコード・合成・UI描画方式だけである。既存初回ロード約23.6 MBの改善は完全に別タスクとし、本章は既存ロード改善効果をGear追加で相殺しないことを保証する。

次は本章の対象外とする。

- `battle-start-logo.png`と同MP4の重複整理
- `title-background-logo-transition.mp4`の最適化
- `rocknroll-one-regular.ttf`のWOFF2化
- 既存preload 19本の整理
- その他の既存asset最適化

本章の実装作業でも、既存preload一覧、既存asset、既存asset形式、既存assetのロード順は変更しない。

### ギアv1アセット予算の正本

次の表をギアv1アセット予算の単一正本とする。転送量は10進のbytes、メモリは2進のMiBで扱う。

| 項目 | 上限 |
|---|---:|
| 初回クリティカルロード増分・目標 | 250,000 bytes |
| 初回クリティカルロード増分・絶対上限 | 500,000 bytes |
| ギアv1専用アセット総量 | 1,000,000 bytes |
| 強化演出素材合計 | 500,000 bytes |
| 単一強化動画 | 350,000 bytes |
| 単一poster | 64,000 bytes |
| 合成済みアイコンcache | 最大64件 |
| 合成済みアイコン推定RGBA memory | 4 MiB |
| Gear icon関連decoded image memory | 8 MiB |
| 強化動画 | 原則2秒以内 / 30fps以下 |

## 12.1 ギアアイコンの構成

6部位 × 8セット × 5レア度 = 240通りの完成画像を個別ファイルとして用意する方式は禁止する。論理構成は、部位6、セット8、レア度最大5の計19 logical partsとする。

物理resourceは原則として次の3 atlasへまとめる。

1. slot atlas
2. set atlas
3. rarity frame atlas

レア度差が色だけなら、neutral maskとCanvas tintを優先する。アイコンは必要時に次の順で合成する。

1. rarity frame
2. slot silhouette
3. set motif
4. stars
5. enhancement level
6. lock / favorite / equipped state

★、強化値、lock、favorite、equipped stateはbitmap cacheへ焼き込まない。cache keyは`slotId | setId | rarityId`とし、on-demandで合成する。240通りの一括生成は禁止する。

ImageBitmap cacheはLRU方式で最大64件、推定RGBA memoryは最大4 MiBとする。Gear icon関連のdecoded image memoryは原則8 MiB以内に抑える。不要なImageBitmapは利用終了後に解放し、cacheをlocalStorageへ保存しない。

## 12.2 ギア素材のロードタイミング

Gearの新規assetを`<link rel="preload">`へ追加してはならない。起動直後はGear assetの取得を開始せず、タイトル画面が安定してからidle queueを開始する。

取得優先順は次のとおり。

1. slot atlas
2. set atlas
3. rarity atlas
4. common decoration
5. small SE
6. optional enhancement effect

GARAGEではdecode、表示中アイコンの合成、audio decodeを進める。Gear画面が準備前に開かれた場合は、表示に必要な最小限だけを優先取得し、同期decodeは行わない。placeholder表示を許容する。

## 12.3 アイドル処理の実行規則

- `requestIdleCallback`が利用可能なら使用するが、必須依存にはしない
- 非対応環境では`setTimeout`等で処理を小分けし、各slice後にevent loopへ制御を返す
- 原則として1 sliceにつき1 heavy taskだけを実行する
- network concurrencyは原則2以下
- image decodeとaudio decodeは、それぞれ原則1件ずつ
- 戦闘中、画面遷移中、オンライン同期中、ユーザー操作中は、未開始のidle taskを抑制する

## 12.4 音声素材

Gear audioは初回再生操作を契機にfetchまたはdecodeしてはならない。タイトル・GARAGEのidle時間に取得し、AudioContextが利用可能になった後、`decodeAudioData`をidle taskとして完了させる。生成したAudioBufferは再利用する。

動画へaudioを埋め込み、同一内容の外部SEも別途持つ重複は禁止する。

## 12.5 倉庫画面の描画

本倉庫500件・一時保管BOX 50件でも全件を毎frame描画しない。virtual scrollを正本とし、描画対象はvisible rowsと、その上1行・下1行だけとする。

次の処理は毎frame実行せず、検索・フィルター・装備・強化などの条件変更時だけ再計算する。

- 全件sort
- 全件filter
- 全件GS calculation
- 全件compare
- 全件text measurement
- 全件icon composition
- 全件Gear validation

巨大なwarehouse CanvasまたはImageBitmapを事前生成してはならない。

## 12.6 初回ロード・アセット容量上限

容量は12章冒頭のアセット予算正本に従う。cache無効時を基準として、初回critical load増分は目標250,000 bytes以下、絶対上限500,000 bytes以下、Gear v1専用アセット総量は1,000,000 bytes以下とする。

既存共有assetはGear専用増分から除外する。ただしGear用に複製した既存assetは増分として含める。Gear専用の新fontは原則禁止する。

## 12.7 強化演出素材

強化演出の実装優先順位は次のとおり。

1. Canvas effect
2. small sprite atlas
3. pre-decodable short video
4. large still image

同一演出をPNGとMP4、WebPとMP4、animated WebPとMP4のように複数形式で重複保持してはならない。posterは軽量fallbackだけに使う。容量は12章冒頭のアセット予算正本に従う。

動画はpreloadせずidle時間に準備し、initial play時のnetwork fetch、audio decode、large image decode、heavy video initializationを禁止する。audioは埋め込まず、原則2秒以内・30fps以下とする。透明演出はCanvasまたはspriteを優先する。

## 12.8 パフォーマンス受入条件

### 起動

- Gear preloadは0件
- 既存preload一覧は変更しない
- critical incrementはアセット予算正本の範囲内
- 240 iconsのupfront compositionは禁止
- title input前のGear audio/video decodeは禁止

### Gear画面

- virtualized drawを使用する
- 240 iconsを事前合成しない
- synchronous decodeを行わない
- 準備中はplaceholderを表示できる

### 強化

idle準備済みなら、強化開始操作時にnetwork fetch、audio decode、large image decode、heavy video initializationを発生させない。Gear起因の50 ms以上のlong taskを発生させない。50 ms条件はruntime acceptanceであり、今回CIは実装しない。

### Warehouse

- visible rowsと上下各1行だけを描画する
- 合成済みcacheを再利用する
- 毎frameの全件validationを行わない

### 検証の自動化

12.6と12.7の上限は、仕様へ記載するだけでは実装完了としない。将来のアセット実装時に、既存の`tests/current-work-state-size.test.js`と同系統の方法で、推奨`tests/gear-asset-budget.test.js`を追加する。

gear-specific asset directoryまたはmachine-readable manifestを正本とし、テスト内だけのmanual asset listは禁止する。CIでは最低限、次を必須検査する。

- Gear v1 dedicated assets totalが1,000,000 bytes以下
- Gear critical assetsが500,000 bytes以下
- enhancement totalが500,000 bytes以下
- single enhancement videoが350,000 bytes以下
- posterが64,000 bytes以下
- Gear preload countが0
- manifest記載assetの欠落はfail
- dedicated directory内の未追跡assetはfail
- 禁止された重複形式はfail

超過時はCI failureとする。第12章の実装完了条件は、通常開発フローでこれらの制約を破れない状態まで作ることである。今回の仕様統合では、このCIテスト自体はまだ作成しない。

## 12.9 将来変更時のルール

新部位、set、rarity、effectを追加しても、完成画像の組み合わせ数をそのままfile countへ増やさない。次の順で検討する。

1. existing part reuse
2. existing atlas extension
3. new small atlas
4. independent large asset

budget超過時は上限引上げより先に、compression、dedup、atlas、Canvas、sharing、lazy loading、optional on-demand assetを検討する。既存asset削減でGear budget超過を相殺してはならない。

# 16. GEAR SCORE

## 16.1 目的

- 個体がどれだけ高品質に育ったかを0〜100で表示
- OPの種類やビルド適性は評価しない
- セット効果やキャラ相性も含めない
- 現在GSと最大到達GSを表示

## 16.2 初期計算式

`GS = 四捨五入(ランク点 + レア度点 + メイン点 + サブ点)`

### ランク点: 最大20

`20 × (★ - 1) / 5`

### レア度点: 最大15

`15 × 初期サブ数 / 4`

### メイン点: 最大20

`20 × 現在メイン値 / 同じ部位・能力の★6+12理論値`

固定値メインは、同じ固定部位の★6+12値を分母にする。

### サブ点: 最大45

★6ミシック+12で、初期4回＋強化4回の計8ロールがすべて最大7%なら合計56。

`45 × min(サブOP数値合計 / 56, 1)`

### 最大到達GS

- 現在の★・レア度は固定
- メインを+12完成値まで伸ばす
- 残りのサブ抽選がすべて該当★の最大値だった場合を加算
- OP種類の優劣は評価しない

## 16.3 表示帯

| GS | 表示 |
|---|---|
| 0〜39 | 通常 |
| 40〜59 | 良品 |
| 60〜79 | 高品質 |
| 80〜89 | 極上 |
| 90〜100 | 神級 |

- GS90以上で自動ロック
- 控えめな発光、専用SE、報酬枠強調
- 派手なカットインはしない

# 23. 保存・機種変更

## 23.1 v1初期

- 端末ローカル保存
- スキーマバージョンを持つ
- 既存データから安全にマイグレーション
- 将来クラウド同期へ移行可能な構造
- コインとギアのように複数キーへまたがる確定操作は、小さなwrite-ahead log（WAL）を先に保存してから反映する
- 起動時にWALが残っていた場合は、途中状態を捨てず、同じ取引IDで前方復旧して読戻し確認後にWALを消す。復旧不能・競合時はWALを保持して通常の書込みを止める

## 23.2 機種変更コード（後期フェーズ）

スマホのみを想定し、JSONファイルではなく文字列コード。

対象:

- ギア
- プリセット
- 粉末
- 設計片
- カタコイン
- キャラ解放
- CPU記録
- 実績
- 協力ボス進捗
- 所持品

仕様:

- 任意4〜6桁PIN
- チェックサム
- 有効期限なし
- 作成日時を復元前に表示
- 古い場合は警告
- 復元前に上書き警告
- 復元直前データを1世代自動退避
- 自動マージなし
- 同じコードを何度でも使用可能
- 未受取報酬がある時は発行不可
- CPU BATTLE中断中は発行不可

### 実装前の測定事項

500ギアを含むコードは長大になる可能性がある。`CompressionStream(gzip)`等で圧縮し、実データ最大時の文字数・コピー成功・復元時間をAndroidで測定してから採用する。

# 25. 整合性監査結果

## 解消済み

1. **タイトル導線**
   - v2.0.142でBATTLE / GARAGE化済み
   - 再実装せずGARAGEへギア項目を追加する

2. **協力ボスの難易度数**
   - 5段階企画を現行3段階へ統合

3. **NORMALの古い戦闘時間**
   - 現行1650HP・12巡を正とし、旧2200HP・20巡へ戻さない

4. **サブ部位制限**
   - 一部部位限定案を撤回し、13種すべて全6部位共通

5. **状態異常命中**
   - 命中OPを削除し、耐性のみ採用

6. **爆風範囲・割合軽減・与ダメージ**
   - 通常OPから外し、セット効果で管理

7. **報酬再抽選**
   - 成果確定時に個体・Seedまで保存

## 実装時に測定・調整が必要

1. 現実的ビルドの実戦差20〜30%目標
2. ★6サブ5〜7%と可変メイン28%の累積火力
3. CPU高連勝がギア成長で簡単になりすぎないか
4. 爆風範囲+8%とノックバック無制限のマップ別影響
5. 500ギア時の保存容量・描画性能
6. 機種変更コードの実文字数
7. GS式が体感と極端に乖離しないか
8. Attack/Defense最終式・丸め順と、固定/可変/サブ/セットを重ねた代表ビルドの実測
