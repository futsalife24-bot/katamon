## 1. 現在のステージシステム

### 1.1 実装方式

**ピクセルマスク方式ではなく、「列ごとの区間リスト」方式**である。ここが本プロジェクトにとって最大の朗報である。

地形の実体は2つある。

| 実体 | 用途 | 定義 |
|---|---|---|
| `segments[列]` | 地形の論理表現。`[[上端Y, 下端Y], ...]` の配列 | 生成時 |
| `solidGrid` | 当たり判定。1セル=1bitの粗いビットマップ | `buildTerrainMask()` が `segments` から焼く |
| `terrainCanvas` | 見た目。オフスクリーンCanvas | 同上 |
| `surfaceY[列]` | 列ごとの最上面Y。歩行の高速参照用 | `rescanColumnsFromGrid()` |

**`segments` は1列に複数の区間を持てる。** つまり多層地形はデータ構造上すでに表現可能である。実際 `tieredBasin`（闘技場マップ）は1列に最大3つの棚を持ち、中央下部は区間ゼロ（＝奈落）で構成されている。

`FREE_TERRAIN_OPTIONS`（`index.html:2930`）に定義。

| キー | 表示名 | 骨格 |
|---|---|---|
| `plateauLeft` | 左高台 | smoothstepで左が高い |
| `plateauRight` | 右高台 | 同・左右反転 |
| `mountainCenter` | 中央山 | `sin(πt)`で中央が高い |
| `valley` | 中央谷 | `sin(πt)`で中央が低い |
| `rolling` | 丘陵 | 平坦＋ノイズのみ |
| `bridge` | 大橋 | 平坦＋中央に薄い橋を上書き |
| `tieredBasin` | 闘技場マップ | **専用関数で3段棚＋中央奈落＋吊り障害物** |

さらに生成時にランダムで重畳される要素がある（`tieredBasin`以外）。

- 薄床ゾーン（35%）
- 浮島 1〜2個（58%）— `islandTop` は最小 y=120 まで上がる
- 地中空洞（30%）— 着弾で偶然開通する
- スタート地点浮島（18%）

### 1.5 地形生成の流れ

```
newTerrain(pattern)
  └ generateTerrain(pattern)
      1. baseCurve(p, t) で骨格の高さ hm[] を作る（380〜600に収まる）
      2. midpointDisplacement でノイズを重ねる（振幅26px、橋9px、闘技場11px）
      3. 両端8列を平滑化（初期足場の安定化）
      4. segments[c] = [[hm[c], FLOOR_Y]] で全列を単一の塊にする
      5. パターン別の上書き
           bridge      → 中央を薄い板に置換
           tieredBasin → buildMortarShelfTerrain() で全面置換
           その他      → 35%で薄床ゾーン
      6. 浮島・空洞・スタート浮島をランダム重畳
      └ 返値 { pattern, segments, startOnIsland, bridge }
  └ buildTerrainMask(segments) で solidGrid と Canvas を焼く
```

## 3. 現在難しいこと

### 3.1 縦の予算が足りない（最大の設計制約）

`baseCurve` の可動域は **380〜600の220pxしかない**。一方 `DEAD_LINE_Y` は636で、最深地形(600)から死線まで36pxしか余裕がない。

つまり「谷を深くする」方向の余地はほぼゼロである。**高低差を増やすなら上方向にしか伸ばせない。**

上方向には余地がある。浮島は y=120 まで到達し、闘技場の壁は y=0 より上まで伸びる。したがって理論上の縦の遊び幅は **120〜636の約516px** で、現在の骨格が使っている220pxの2.3倍ある。

**結論**: 高低差拡張は `GROUND_MIN_Y` を下げる（＝上へ伸ばす）か、`baseCurve` を経由せず `segments` を直接組む方式で行う。後者は `buildMortarShelfTerrain()` という実装見本がすでにある。

### 3.2 CPUが地形の遮蔽を一切見ていない（最大の実装リスク）

`cpuAutoTurn()` → `perfectAimVelocity()`（`index.html:6483-6493`）は、**放物線の解析解を1回解くだけ**である。

```js
const vx0 = ((dx - 0.5 * windAccel * t * t) / t) / launchSpeedMul;
const vy0 = ((dy - 0.5 * gravity * t * t) / t) / launchSpeedMul;
```

滞空時間 `t` は**水平距離だけ**から決まる（`距離/300` を 0.72〜2.2 に丸める）。

コード全体を検索した結果、**射線の遮蔽判定（line of sight）はどこにも存在しない**。`isSolidAt()` の呼び出しは弾の衝突判定（`index.html:10427`）と闘技場の壁だけである。

**帰結**: 山・柱・上層の床など、両者の間に高い遮蔽物があるステージでは、CPUは山肌へ撃ち込み続ける。現状の `mountainCenter` でも同じ問題は起きているが、山が低く（最大220px）滞空時間も長めなため偶然越えることが多く、表面化していないだけである。

**中央巨大柱・二層遺跡・崩壊都市は、この問題を解かない限りCPU戦が成立しない。**

なお `cpuStepIsSafe()`（`index.html:6448`）で「歩いて奈落へ落ちない」対策は済んでいる。これは闘技場導入時にCPUが自滅した実績があるため後付けされたもので、**新地形を入れるたびに同種の穴が出る**と考えるべきである。

### 3.3 オンライン同期は地形を丸ごと送っている

`buildSnapshot()` は `segments` 全480列と `craterHistory` を含み、これが `start` と毎ターンの `state` で送られる。

実測したJSONサイズ:

| 構成 | サイズ |
|---|---|
| 単層（現行の通常ステージ） | 約 8.2 KB |
| 二層 | 約 13.4 KB |
| 三層 | 約 20.2 KB |

**多層化はターンごとの通信量を1.6〜2.5倍にする。** スマートフォンの回線を考えると、三層構成を常時同期する設計は避けるべきである。

さらに既知の落とし穴がある。RTDBは空配列・nullをキーごと保存しないため、区間ゼロの列（＝奈落）は復元時に消える。`tests/stage3test.js:82-100` にこの正規化の回帰テストがあり、橋の `bridge: null` で実機不具合が出た記録も残っている（同ファイル105行）。**多層・空洞を増やすほどこの地雷を踏む機会が増える。**

### 3.4 新ステージ追加は必ずFirebase Console作業を伴う

地形キーを1つ増やすと、以下すべての更新が必要になる。

| 箇所 | 内容 |
|---|---|
| `index.html:1526` `baseCurve()` | 骨格の追加 |
| `index.html:1686` `generateTerrain()` のランダム配列 | 抽選対象に入れるか |
| `index.html:2930` `FREE_TERRAIN_OPTIONS` | 演習・オンラインのUI選択肢 |
| `index.html:3685` `SNAPSHOT_PATTERNS` | **これを忘れるとスナップショット検証で弾かれる** |
| `database.rules.json` 21行 `settings.terrain` の列挙 | **これを忘れると部屋設定が保存できない** |
| **Firebase Console** | 上記ルールの反映 |

**この最後の1行が今回のv91ブロッカーそのものである。** `useJump` をルールへ追加したがConsoleへ反映されておらず、初回砲撃が全て401で拒否された（Issue #2）。地形追加は同じ経路を毎回通る。ステージを増やすほど、この事故の再発機会が増える。

### 3.5 その他の制約

- **`solidGrid` の解像度**: 3px×4pxのセル。厚さ4px未満の床は表現できない。「薄い足場」の下限は実質8〜12px（現行の橋は `thinDepth = 8〜13px`）。
- **y<0 は破壊不能**: 地形Canvasが y=0 から下にしか存在しない。画面上端より上の壁は「壊れない岩盤」として2026-07-29にユーザー合意済み。
- **地形は全画面1枚のCanvas**: 破壊のたびに `rescanColumnsFromGrid()` が影響列のみ再走査するので軽いが、`rebuildTerrainRim()` が毎回走る。広範囲の連続崩落を実装すると負荷が集中する。
- **落下ダメージが無い**: 「高所は落下リスクが大きい」というバランスは、**現状では場外死しか手段がない**。中間的なリスクを作るには新規実装が要る。
- **キャラの砲口＝中心**: `unitAnchor()` は `{x: u.x, y: u.y}` を返すだけ。射角の制限も無く、引っ張り方向で360°撃てる。地形に埋まった状態での発射制限は無い。

## 5. オリジナル5ステージの実現性評価

### A. 三連峰 — **採用（最優先）**

- 難易度 2 / 効果 4 / 流用率 90%
- `baseCurve` に低・中・高の3峰を書くだけで骨格は完成する。
- ただし現行 `GROUND_MIN_Y`=380 のままでは峰が低すぎて「高度差が戦術になる」水準に届かない。**`baseCurve` の戻り値クランプを緩め、最高峰を y=260 前後まで上げる必要がある**（`clampGround` の見直し）。
- 燃料102＝102pxなので、峰から峰への移動は1ターンでは届かない設計が可能。移動判断が自然に生まれる。
- **CPU遮蔽問題が初めて実測できるステージ**であり、その意味で最も価値が高い。

### B. 風切り高原 — **採用（ただし簡易方式に限る）**

- 難易度 3 / 効果 4 / 流用率 70%
- 風の適用は `index.html:10318` の1行 `p.vx += windAccel * dt` に集約されている。**高度係数を掛けるのはこの1箇所で足りる。**
- 完全な高度別風（連続関数）は不要。**2段階または3段階の階段関数**を推奨する。

  ```
  高度係数 = p.y < 高空境界 ? altitudeWindScale : 1.0
  ```

- 同期への影響: 風は `snapshot.wind` で共有済み。境界値と係数を**ステージ定義側の定数**に持てば、パケットは増えない。
- **CPUへの影響が重い**。`perfectAimVelocity()` は風を定数として解析解に入れている。高度で風が変われば解析解は成立しなくなる。CPUだけ平均風で近似する妥協が要る（実用上は許容範囲）。
- 注意: これは「ギミック」ではなく**物理法則の変更**である。1ステージ限定にするか全ステージ共通にするかは設計判断であり、後述の未確定事項に含める。

### C. 天空水道橋 — **保留（Cの前にBを）**

- 難易度 4 / 効果 5 / 流用率 65%
- `segments` の多層性と `addFloatingIsland` で形は作れる。落下・足場破壊も既存機構で動く。
- 障害は3つ。
  1. 同期量が1.6〜2倍（3.3）
  2. 空列のRTDB null落ち（3.3）
  3. CPUが上層の床を撃ち抜けず、また上層から落ちる（3.2＋`cpuStepIsSafe`の拡張）
- 三連峰と風切り高原でCPU射線と縦予算の目処が立ってから着手すべき。

### D. 二層遺跡 — **保留**

- 難易度 4 / 効果 5 / 流用率 60%
- 技術的には天空水道橋とほぼ同じ課題。違いは「上層の床が破壊対象になる」点で、これは `carveCrater` がそのまま使える。
- **`walkableGroundYAt()` と `groundYBelow()` がすでに多層対応済み**なのが強い。実装の本体は地形生成とCPUであって、キャラ物理ではない。

### E. 崩壊都市 — **却下（現時点）／将来の再評価対象**

- 難易度 5 / 効果 5 / 流用率 40%
- 三層構造の同期量は約20KBで、ターンごとに送るには重い。差分同期の導入が前提になる。
- 依頼文自身が「必要技術が揃った後の最終候補」としており、その判断に同意する。
- **再評価条件**: (1) CPU射線判断の実装完了、(2) 地形差分同期の導入、(3) 二層遺跡の実機QA通過。

## 6. 必要な基盤改修

### 6.1 最小限必要（三連峰の実装に必須）

1. **縦予算の解放** — `baseCurve` の出力を `GROUND_MIN_Y`(380) で頭打ちにしている `clampGround` を、ステージ単位で緩められるようにする。既存6ステージの見た目は変えないこと。
2. **ステージ定義の一元化** — 現在ステージ固有の値が `baseCurve`、`generateTerrain`、`FREE_TERRAIN_OPTIONS`、`buildTerrainMask` の配色分岐、BGM分岐（`index.html:690`）、背景分岐（`index.html:1046`）に散在している。`tieredBasin` は6箇所以上に `if` が書かれており、**このまま新ステージを足すと分岐が線形に増える**。
   1つの `STAGE_DEFS` テーブルへ、少なくとも「骨格関数・ノイズ振幅・縦予算・BGM・背景・浮島の可否」を集約すべき。**依頼文11章の「ステージごとの調整値をコードへ散在させない」に直接対応する。**

### 6.2 将来を考慮して今から形を決めておくもの

3. **CPUの射線判定** — `perfectAimVelocity()` の後段に、求めた初速で弾道を粗くサンプリングし `isSolidAt()` で遮蔽を見る検査を足す。遮蔽されていれば `t` を変えて数回リトライする。
   - 現行が1回の解析解なので、**5〜8回のリトライでも計算量は無視できる**（1ターンに1回しか呼ばれない）。
   - これは三連峰の時点では「あれば良い」だが、柱・二層では必須。**形だけ先に入れておくのが安い。**
4. **地形パラメータの持ち方** — 依頼文8章の候補を現行構造と突き合わせた判断は次のとおり。

| パラメータ | 判断 | 理由 |
|---|---|---|
| `terrainHardness` | **不要（当面）** | `carveCrater` は半径固定。硬さは半径係数1つで足り、領域単位の管理は過剰 |
| `surfaceFriction` | **却下** | 現行に慣性が無い（`MOVE_SPEED`固定）。摩擦を入れると移動系の全面改修になる |
| `altitudeWindEnabled` / `altitudeWindScale` | **採用（風切り高原で）** | ステージ単位。1箇所の乗算で済む |
| `collapseThreshold` | **保留** | 崩落は魅力的だが、連鎖処理と同期の設計が要る |
| `fallDeathY` | **採用** | 現在 `DEAD_LINE_Y` がグローバル定数。ステージ単位にする価値がある |
| `minimumSafeThickness` | **不要** | `solidGrid` の解像度(4px)が事実上の下限を決めている |
| `spawnAltitudeRange` | **採用** | 現在スポーンは x=15%/85% 固定で高さは地形任せ。多層では初期配置の公平性に直結 |
| `indestructibleRegions` | **採用（形だけ）** | 闘技場の壁がすでに事実上これ。`arenaWallSolidAbove()` の一般化 |
| `fragileRegions` | **保留** | 崩落とセット |

**表現方式の結論**: マスク画像は採用しない。理由は (1) `segments` が既に論理表現として機能している、(2) 画像だと中断セーブ・オンライン同期に載せられない、(3) 破壊後の状態が `craterHistory` で再現される現行設計と噛み合わない。**データ構造（`STAGE_DEFS` テーブル）で表現する。**

### 6.3 今は不要

- 地形の差分同期（崩壊都市の前提。二層までは全体同期で足りる）
- 落下ダメージ（高所リスクは場外死と射線露出で作れる。入れるならバランス再設計を伴う）
- 動くリフト・噴火・落石（ターン制の同期設計が別途必要。優先度は最後）

## 8. 推奨する最初の1ステージ：三連峰

### 選定理由

1. **既存コードの流用率が最も高い**（`baseCurve` への追加が本体）。
2. **高低差という本プロジェクトの主目的を、最小の変更で直接検証できる。**
3. **CPU射線問題を初めて実測可能な形で表面化させる**。この問題は柱・二層・崩壊都市すべての前提条件であり、最も安いステージで先に踏むべきである。
4. **「新ステージ追加の手順」をコストの低い題材で1度通せる。** 特に `database.rules.json` → Firebase Console 反映という、今回のv91で事故が起きた経路を、影響の小さい題材で確立できる価値が大きい。

### 検証できる技術

- 縦予算の解放（`GROUND_MIN_Y` 制約の緩和）が既存ステージを壊さないか
- 58°登坂制限と峰の斜面の相性
- 燃料102pxと峰間距離の釣り合い（移動判断が生まれるか）
- 跳躍（v91の新機能）が峰越えに使えるか
- CPUの遮蔽問題の実測
- ステージ追加の全経路（UI・スナップショット検証・ルール・Console）

### 実装対象

| 対象 | 変更 |
|---|---|

## 9. 未確定事項（ユーザー判断が必要）

### 9.1 計画順序（最重要）

本テーマは承認済みロードマップに存在しない。以下の判断が必要である。

- 先行残タスク（Issue #2〜#8）より先に着手するか、後にするか
- 後にする場合、採用企画16件（v101〜v121）のどこへ挿入するか
- `boom` 権威座標同期（Issue #3 / v92）は多層地形で重要度が上がる。**多層ステージを入れるなら Issue #3 は必ず先に完了させるべき**である

### 9.2 設計判断

1. **風切り高原の適用範囲** — 高度別風を「1ステージ限定のギミック」にするか、「全ステージ共通の物理法則」にするか。後者は既存6ステージのバランスを全て変える。
2. **落下ダメージの是非** — 高所の欠点を作る手段。現在は場外死のみ。導入するとキャラのHP設計に影響する。
3. **縦予算の解放幅** — 最高峰をどこまで上げるか。上げるほどカメラのズーム操作と視認性に影響する（既存の視点距離記憶機能との兼ね合い）。
4. **既存6ステージを高低差方向へ作り直すか** — 新ステージだけ高低差が大きいと、既存ステージが見劣りする可能性がある。
5. **ランダム抽選への組み込み** — 新ステージを `generateTerrain` のランダム対象に入れるタイミング。オンラインQAが済むまでは入れないことを推奨する。

### 9.3 コードだけでは判断できないこと

- 実機（スマートフォン）で、y=260の高峰と y=600 の谷が1画面に収まって読めるか。**自動テストでは判定できない**（`tests/README.md` にも「色や配置の最終判断は実機で目視すること」とある）。
- 燃料102pxが多層ステージで「足りない」と感じるか「ちょうどよい」と感じるか。
- 三層構成（崩壊都市）の20KB同期が、実際の回線で許容できるか。

## 10. 総括

**良い知らせ**: 地形データ構造（列ごとの区間リスト）はすでに多層に対応しており、歩行・落下・破壊の各処理も多層対応済みである。`tieredBasin` という多層ステージの実装見本もある。**基本地形12種のうち6種は `baseCurve` への追加だけでほぼ実装できる。**

**悪い知らせ**: 本プロジェクトの本命である高低差・多層ステージの障害は、地形生成ではなく次の3点に集中している。

1. **CPUが射線の遮蔽を見ていない**（山・柱・二層のすべてを塞ぐ）
2. **縦の予算が220pxしかない**（高低差そのものが足りない）
3. **ステージ固有の分岐が6箇所以上に散在**（増やすほど保守不能に近づく）

いずれも三連峰1ステージの実装過程で、小さく安全に解決できる。**最初にステージを増やすのではなく、この3点を三連峰という最小の題材で片付けることを推奨する。**
