# コンテキスト効率化型 開発ワークフロー

## 目的

調査精度と安全性を維持しながら、不要な全文読み込み、重複調査、過剰なテストによるコンテキスト使用量と実行時間を抑える。

この文書は、`AGENTS.md`の「大容量ファイルとコンテキストの読み込み方針」に対する詳細手順の正本であり、このプロジェクトのすべてのCodexセッション、worktree、開発、調査、コードレビュー、修正へ適用する。

## 基本フロー

ファイルを調べるときは、原則として次の順序で進める。

1. `SEARCH`: ファイルサイズと行数を確認し、`rg`、`grep`、`find`等でキーワード、関数名、クラス名、見出し、キーを検索する。
2. `LOCATE`: 検索結果、定義一覧、関数一覧、見出し一覧、キー一覧から、根拠になり得る箇所を特定する。
3. `SLICE`: `head`、`tail`、`sed`、`awk`、PowerShell、Python等で必要な行、範囲、項目だけを抽出する。
4. `REASON`: 抽出した根拠から判断し、情報が不足する場合だけ隣接範囲または次の関連箇所へ読み取りを広げる。

大容量ファイルを`cat`等で無条件に全文表示しない。「念のため」の全文読み込みや、一度取得した情報の不要な再読み込みも行わない。全文確認が本当に必要な場合のみ、適切な範囲へ分割して読む。

## 長大な文書と構造化ファイル

- `CURRENT_WORK_STATE.md`、README、仕様書、履歴、HANDOFF等が長大な場合も、最初に見出しと関連語を検索し、現在の作業に必要な箇所を優先する。
- 全体構造の把握が目的なら、全文ではなく、見出し、定義、関数、クラス、キーの一覧を先に抽出する。
- JSON、CSV、ログ、生成ファイル、ロックファイル等は、原則としてプログラムで必要なキー、列、レコード、集計値、エラー周辺だけを抽出する。
- 既に取得済みの結果は再利用し、状態変化の確認が必要な場合を除いて同じ内容を繰り返し読み込まない。

## 検証の選び方

- 変更範囲に対応するtargeted testを優先する。
- GitHub CIがfull regressionを担う場合、ローカルで同一のfull regressionを理由なく重複実行しない。
- 影響範囲が広い、CIで確認できない、失敗時の損失が大きい等の理由がある場合は、必要な追加検証を行う。
- 文書だけの変更は、原則として`git diff --check`、Markdown構造、参照リンク、変更ファイル範囲を確認する。

## 正確性と安全性の優先

security、authority、認証・認可、アクセス制御、秘密情報、課金、公開、削除、データ移行等では、トークン節約より正確性と安全性を優先する。ただし最初から無条件に全文を読むのではなく、基本フローで範囲を絞り、判断に必要な根拠が揃うまで段階的に読み取り範囲と検証を広げる。
